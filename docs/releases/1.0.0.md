## 从编译器到项目管理器 / From compiler to project manager

**1.0.0 把 xmlsquish 定义为 XML Prompt 的本地优先、确定性项目管理器。** 编译器仍是核心引擎，但项目创建、格式化、构建、依赖变更、工作区与产物检查现在共享同一套有类型的调度、诊断和恢复模型。

**1.0.0 defines xmlsquish as a local-first, deterministic project manager for XML prompts.** The compiler remains its core engine, while project creation, formatting, builds, dependency changes, workspaces, and artifact inspection now share one typed scheduling, diagnostic, and recovery model.

```text
new → add/remove → fmt → build → inspect
```

### 完整性与平台信任 / Integrity and platform trust

解压前，以准确文件名对应 `SHA256SUMS` 中的一行：Linux 使用 `sha256sum <archive>`，macOS 使用 `shasum -a 256 <archive>`，PowerShell 使用 `Get-FileHash -Algorithm SHA256 <archive>`。校验和证明下载字节的完整性，不证明发布者身份。

Before extraction, compare the row for the exact filename in `SHA256SUMS`: use `sha256sum <archive>` on Linux, `shasum -a 256 <archive>` on macOS, or `Get-FileHash -Algorithm SHA256 <archive>` in PowerShell. Checksums establish byte integrity, not publisher identity.

当前二进制未做代码签名（code signing）或 Apple 公证（notarization），系统可能显示安全提示；不要为安装关闭全局安全保护。发布归档包含 GPL 许可证及第三方依赖法律声明。

The binaries are currently unsigned and not Apple-notarized, so an operating-system warning may appear; do not disable system-wide protections. Release archives include the GPL license and third-party dependency notices.

## 第一个项目 / First project

```console
xmlsquish new hello
cd hello
xmlsquish fmt --check
xmlsquish build --offline
```

`new` 默认采用 Git；若不需要版本控制，使用 `xmlsquish new hello --vcs=none`。目标必须尚不存在，已有目录不会被覆盖。面向已有目录的 `init` 不是 1.0.0 的命令。

`new` uses Git by default; use `xmlsquish new hello --vcs=none` when version control is unwanted. The destination must not exist and is never overwritten. An `init` workflow for existing directories is not part of 1.0.0.

## 六个稳定命令 / Six stable commands

| 命令 / Command | 产品职责 / Product responsibility |
|---|---|
| `new` | 原子创建可立即格式化、离线构建的规范项目 / Atomically create a canonical, immediately formattable and offline-buildable project |
| `fmt` | 通过保留语义的 XML 具体语法树格式化；支持 `--check` 与 `--diff` / Format through a semantics-preserving XML concrete syntax tree; supports `--check` and `--diff` |
| `build` | 解析、编译、链接并原子发布目标产物 / Resolve, compile, link, and atomically publish target artifacts |
| `add` | 以可恢复事务加入依赖并协调清单与锁文件 / Add a dependency while transactionally coordinating manifest and lock state |
| `remove` | 以可恢复事务移除依赖；不隐式修改 XML import / Remove a dependency recoverably without implicitly editing XML imports |
| `inspect` | 检查构建、链接、来源与产物信息，不改变项目 / Inspect build, link, provenance, and artifact information without changing the project |

所有命令使用直接形式 `xmlsquish COMMAND`；1.0.0 不再支持把第一个位置参数解释为松散 XML 输入文件。

All commands use the direct `xmlsquish COMMAND` form. Version 1.0.0 no longer interprets the first positional argument as a loose XML input file.

## 项目、工作区与依赖 / Projects, workspaces, and dependencies

- `xmlsquish.toml` 是版本化项目契约，支持向上发现和显式 `--manifest-path`。
- 工作区可以选择包、继承依赖，并在 `new` 创建成员时保持一致。
- 路径、Git、registry 与工作区继承依赖由解析器统一处理；`xmlsquish.lock` 固化机器选择的精确状态。
- `--locked` 禁止锁状态漂移，`--offline` 禁止网络获取，`--frozen` 同时约束两者。
- 配置优先级是 defaults < user < workspace < environment < CLI；可重复的 `--config KEY=VALUE` 接受 TOML 值。

- `xmlsquish.toml` is the versioned project contract, with upward discovery and explicit `--manifest-path` selection.
- Workspaces select packages, inherit dependencies, and remain consistent when `new` creates a member.
- Path, Git, registry, and workspace-inherited dependencies share one resolver; `xmlsquish.lock` records the exact machine-selected state.
- `--locked` prevents lock-state drift, `--offline` prevents network fetches, and `--frozen` applies both constraints.
- Configuration precedence is defaults < user < workspace < environment < CLI; repeatable `--config KEY=VALUE` accepts TOML values.

## 事务性 `new` 与恢复 / Transactional `new` and recovery

`new` 不是逐个复制模板文件。它先在同一文件系统的暂存区构造并验证完整候选项目，再通过排他原子重命名发布；若加入外围工作区，还使用持久日志协调项目发布与成员登记。竞争者先创建目标时，本进程失败而不覆盖对方数据。

`new` does not copy template files one at a time. It constructs and validates a complete candidate in same-filesystem staging, then publishes through an exclusive atomic rename. When joining an enclosing workspace, a durable journal coordinates project publication and member registration. If a competitor creates the destination first, this process fails without overwriting the competitor.

取消发生在提交前时不发布项目并退出 `130`。若取消在不可逆提交后到达，xmlsquish 先恢复一致状态，再以延迟取消结果结束。受控进程终止的恢复边界已由故障注入测试覆盖。

Cancellation before commit publishes no project and exits `130`. If cancellation arrives after irreversible commit, xmlsquish restores a consistent state before completing with a deferred-cancellation result. Fault-injection tests cover recovery from controlled process termination boundaries.

## 可检查的产物 / Inspectable artifacts

构建默认发布 `.prompt`，并可重复使用 `--emit prompt|ir|debug` 选择：

Builds publish `.prompt` by default and accept repeatable `--emit prompt|ir|debug` selections:

| 后缀 / Suffix | 含义 / Meaning |
|---|---|
| `.prompt` | 最终可消费 Prompt / Final consumable prompt |
| `.xsir` | 可复用的类型化中间表示（Intermediate Representation, IR）/ Reusable typed intermediate representation |
| `.psdbg` | 自包含的来源与调试证据 / Self-contained provenance and debugging evidence |

构建状态使用内容寻址缓存（content-addressed cache），发布使用原子替换。`inspect` 面向人类返回可读视图，或以 `--format json` 返回单一机器查询文档。

Build state uses content-addressed caching and atomic publication. `inspect` returns a human-readable view or one machine-readable query document with `--format json`.

## 自动化、IDE 与协议 2.1 / Automation, IDEs, and protocol 2.1

操作输出可选 `human`、`short` 或版本化 NDJSON `json`。原生事件信封为协议 `2.1`，包含调用标识、单调序号和有类型 payload；2.1 增加 `new` 的项目目的地、创建结果和延迟取消事件。消费者必须按协议的加法演进规则忽略未知的可选事件，而不能解析人类终端文字。

Operation output supports `human`, `short`, and versioned NDJSON `json`. The native event envelope is protocol `2.1`, with invocation identity, monotonic sequence, and typed payloads. Version 2.1 adds project-destination, creation-result, and deferred-cancellation events for `new`. Consumers must follow the protocol's additive evolution rule and skip unknown optional events rather than parsing human terminal prose.

稳定退出码 / Stable exit codes:

| Code | Meaning |
|---:|---|
| `0` | 成功 / Success |
| `1` | 领域失败，包括 dirty `fmt --check` / Domain failure, including dirty `fmt --check` |
| `2` | 命令用法错误 / CLI usage error |
| `130` | 取消 / Cancellation |
| `101` | 未映射内部错误 / Unmapped internal error |

## 从 0.3.0 迁移 / Migrating from 0.3.0

1. 为源码建立 `xmlsquish.toml`，把每个可构建入口声明为目标。
2. 把旧的松散文件调用迁移为 `xmlsquish build`，必要时指定 `--manifest-path`、包和目标。
3. 不再依赖源码旁边的旧中间或最终文件；从项目 `target/` 消费 `.prompt`、`.xsir` 或 `.psdbg`。
4. 将自动化迁移到协议 2.1 NDJSON 和稳定退出码，不要抓取 human renderer 输出。
5. 保留现有 0.3.0 XML DSL 命名空间；本次发布改变项目与命令模型，不改变 XML DSL 原语和含义。

1. Add an `xmlsquish.toml` manifest and declare each buildable entry as a target.
2. Replace loose-file invocations with `xmlsquish build`, selecting a manifest, package, or target when needed.
3. Stop consuming legacy sibling intermediate/final files; consume `.prompt`, `.xsir`, or `.psdbg` from project `target/` state.
4. Move automation to protocol 2.1 NDJSON and stable exit codes instead of scraping the human renderer.
5. Keep the existing 0.3.0 XML DSL namespace. This release changes the project and command model, not the XML DSL primitives or their meaning.

1.0.0 的版本承诺从这里开始：后续兼容版本不会无预警破坏已声明的命令、清单、产物、协议和退出码契约。0.3.0 的历史文档和命名空间仍永久可引用；这不意味着旧 CLI 调用形式继续受支持。

The 1.0.0 stability commitment begins here: subsequent compatible releases will not silently break the declared command, manifest, artifact, protocol, and exit-code contracts. Historical 0.3.0 documentation and namespaces remain permanently addressable; this does not preserve the old CLI invocation forms.

## 已知限制 / Known limitations

- `new` 只创建尚不存在的目标；1.0.0 没有 `init` 或覆盖模式。
- 仓库和二进制不发布到 crates.io。
- 二进制未签名且未经过 Apple 公证。
- 受控进程终止后的恢复已有测试；不主张已经证明突然断电、存储控制器缓存或任意远程文件系统的持久性。
- 排他原子重命名依赖平台和文件系统支持；不支持时明确失败，不使用存在竞争窗口的模拟回退。

- `new` only creates absent destinations; 1.0.0 has no `init` or overwrite mode.
- The workspace and binaries are not published to crates.io.
- Binaries are unsigned and not Apple-notarized.
- Recovery after controlled process termination is tested; durability across sudden power loss, storage-controller caches, or arbitrary remote filesystems is not claimed.
- Exclusive atomic rename depends on platform and filesystem support; unsupported environments fail explicitly rather than using a race-prone emulation.

## 发布可复现性 / Release reproducibility

GitHub Actions 从不可移动的 `v1.0.0` 标签提交，在六种原生目标上使用 Rust 1.88 锁定构建、运行测试和 CLI smoke test，然后才汇总发布资产。发布脚本要求 Cargo 版本、二进制 `--version` 与标签一致，要求六种资产齐全，并拒绝覆盖同名但字节不同的既有资产。

GitHub Actions builds the immutable `v1.0.0` tag commit with locked Rust 1.88 dependencies on six native targets, runs tests and CLI smoke tests, and only then aggregates release assets. Automation requires Cargo metadata and binary `--version` to match the tag, requires the complete six-asset matrix, and refuses to replace an existing same-named asset with different bytes.
