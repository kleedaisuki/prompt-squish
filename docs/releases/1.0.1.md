## 发布边界成为产品契约 / Publication boundaries become product contracts

**1.0.1 用有类型的发布目录取代了对发布器物理布局的推断。** 每个成功提交的目标都提供稳定的项目相对逻辑定位符，可原样交给 `inspect artifact`。generation 目录、journal、current pointer 和内部 hash 仍属于发布器，不再是人类输出或机器协议的一部分。

**1.0.1 replaces inference over publisher storage layout with a typed publication catalog.** Every successfully committed target supplies stable, project-relative logical locators that can be passed verbatim to `inspect artifact`. Generation directories, journals, current pointers, and internal hashes remain publisher-owned and are no longer part of human output or the machine protocol.

```console
$ xmlsquish build --emit=prompt --emit=ir --emit=debug
$ xmlsquish inspect artifact target/xmlsquish/prompt.prompt --format=raw > prompt.xml
```

`--format=raw` 只适用于 `inspect artifact`。xmlsquish 在输出任何字节前解析发布目录、读取真实产物并验证其摘要和大小；stdout 不包含元数据或状态文本。

`--format=raw` is valid only for `inspect artifact`. xmlsquish resolves the publication catalog, reads the real artifact, and verifies its digest and size before writing any bytes; stdout contains no metadata or status prose.

### 完整性与平台信任 / Integrity and platform trust

解压前，以准确文件名对应 `SHA256SUMS` 中的一行：Linux 使用 `sha256sum <archive>`，macOS 使用 `shasum -a 256 <archive>`，PowerShell 使用 `Get-FileHash -Algorithm SHA256 <archive>`。校验和证明下载字节的完整性，不证明发布者身份。

Before extraction, compare the row for the exact filename in `SHA256SUMS`: use `sha256sum <archive>` on Linux, `shasum -a 256 <archive>` on macOS, or `Get-FileHash -Algorithm SHA256 <archive>` in PowerShell. Checksums establish byte integrity, not publisher identity.

当前二进制未做代码签名（code signing）或 Apple 公证（notarization），系统可能显示安全提示；不要为安装关闭全局安全保护。发布归档包含 GPL 许可证及第三方依赖法律声明。

The binaries are unsigned and not Apple-notarized, so an operating-system warning may appear; do not disable system-wide protections. Release archives include the GPL license and third-party dependency notices.

## 主要变化 / Highlights

### 有类型的发布目录 / Typed publication catalog

- 目标发布结果明确携带 `target_id`、`generation_id` 和产物列表。
- 每个产物携带不可变 `id`、类型 `kind`、稳定 `locator`、`size` 和 `digest`。
- 重新构建可以改变 generation 和内容身份，但同一宣告产品的逻辑定位符保持稳定。
- manager 不再构造、解析或扫描发布器的私有目录。

- Target publication results explicitly carry `target_id`, `generation_id`, and their artifact list.
- Each artifact carries immutable `id`, typed `kind`, stable `locator`, `size`, and `digest` fields.
- A rebuild may change generation and content identity while preserving the logical locator for the same declared product.
- The manager no longer constructs, parses, or scans publisher-private directories.

### 可注入、按能力延迟初始化的运行时 / Injected, capability-lazy runtime

`ProductionHost` 在组合边界创建一个 invocation-scoped `ProductionBuildRuntime`，manager 只依赖有类型端口。CAS、action index、target publisher 与 catalog publisher 分别通过可重试的 single-flight cell 延迟初始化。因此，仅运行编译、链接、实例化或 descriptor 计算的路径不会创建存储目录；某一能力的初始化失败也不会污染其他能力。

`ProductionHost` creates one invocation-scoped `ProductionBuildRuntime` at the composition boundary, while the manager depends only on typed ports. CAS, the action index, the target publisher, and the catalog publisher each initialize lazily through retryable single-flight cells. Compile-, link-, instantiate-, and descriptor-only paths therefore create no storage directories, and one capability's initialization failure does not poison unrelated capabilities.

### 可执行的架构边界 / Executable architecture boundary

CI 现在将 `cargo metadata` 中的实际 workspace 依赖图与受评审的边策略比较。已禁止的边、未审批的新边和已失效的 allowlist 边都会使检查失败；checker 本身也有 fixture 自测。这使 runtime 组合和发布存储责任的分离成为可持续验证的契约，而不只是文档约定。

CI now compares the real workspace dependency graph from `cargo metadata` with a reviewed edge policy. Forbidden edges, unapproved new edges, and stale allowlisted edges all fail the check, and fixtures test the checker itself. Separation between runtime composition and publication storage ownership is therefore continuously executable rather than documentation-only.

## **必须采取行动：协议 3.0 迁移** / **Action required: protocol 3.0 migration**

> **重要：** 1.0.1 的产品版本只增加了补丁号，但 `--message-format=json` 的原生机器协议从 1.0.0 的 `2.1` 升级为 `3.0`。这不是可加性更改。如果自动化解析构建结果，请在升级 CLI 时同步迁移消费者。

> **Important:** the product version advances only by a patch, but the native `--message-format=json` machine protocol moves from `2.1` in 1.0.0 to `3.0`. This is not an additive change. If automation parses build results, migrate the consumer together with the CLI upgrade.

v3 `operation_completed` 构建结果的核心结构是：

```text
BuildResult {
    published: [PublishedTarget {
        target,
        target_id,
        generation_id,
        artifacts: [PublishedArtifact { id, kind, locator, size, digest }]
    }],
    build_record
}
```

| 1.0.0 / protocol 2.1 | 1.0.1 / protocol 3.0 | 迁移要求 / Migration |
|---|---|---|
| `PublishedTarget.artifacts[]` 为通用 `Artifact` | 为有类型 `PublishedArtifact` | 按新结构解码，不要将 v2 当作 v3 |
| 产物 `uri` 可能暴露物理 generation 路径 | 产物提供稳定逻辑 `locator` | 保存并原样传递 `locator` |
| 目标缺少完整发布身份 | 目标提供 `target_id` 和 `generation_id` | 以有类型字段做关联，不要解析路径 |
| 没有完整产物字节查询 | `inspect artifact LOCATOR --format=raw` | 需要字节时调用查询，不要读取私有目录 |

v3 仍使用 `{major, minor}` 版本对象、invocation-local 单调 `sequence` 以及 `payload.type` / `payload.data` 的有类型判别结构。同一受支持主版本中的未知可选事件可跳过；不得因为 v2 和 v3 共享部分生命周期事件，就把 v2 构建结果当作 v3。

v3 retains the `{major, minor}` version object, invocation-local monotonic `sequence`, and typed `payload.type` / `payload.data` discriminator. Unknown optional events within a supported major may be skipped; a consumer must not treat a v2 build result as v3 merely because the versions share some lifecycle events.

## 不变的契约 / Unchanged contracts

- 六个直接命令仍是 `new`、`fmt`、`build`、`add`、`remove` 和 `inspect`。
- `xmlsquish.toml`、锁定/离线模式、稳定退出码和 `.prompt` / `.xsir` / `.psdbg` 产物角色保持不变。
- XML DSL 的命名空间 URI、原语和语义没有改变。
- Rust 最低支持版本仍是 1.88。

- The six direct commands remain `new`, `fmt`, `build`, `add`, `remove`, and `inspect`.
- `xmlsquish.toml`, locked/offline modes, stable exit codes, and the `.prompt` / `.xsir` / `.psdbg` artifact roles are unchanged.
- The XML DSL namespace URI, primitives, and semantics are unchanged.
- The minimum supported Rust version remains 1.88.

## 已知限制 / Known limitations

- 仓库和二进制不发布到 crates.io。
- 二进制未签名且未经 Apple 公证。
- 发布目录提供逻辑产物真相；它不把内部 generation 路径提升为持久用户 API。
- 突然断电、存储控制器缓存和任意远程文件系统的持久性不在已证明范围内。

- The workspace and binaries are not published to crates.io.
- Binaries are unsigned and not Apple-notarized.
- The publication catalog is the logical artifact truth; internal generation paths are not a durable user API.
- Durability across sudden power loss, storage-controller caches, or arbitrary remote filesystems is not claimed.

## 发布可复现性 / Release reproducibility

GitHub Actions 从不可移动的 `v1.0.1` 标签提交，在六种原生目标上使用 Rust 1.88 锁定构建、运行测试和 CLI smoke test，然后才聚合发布资产。发布脚本要求 Cargo 版本、二进制 `--version` 与标签一致，要求六种资产齐全，并拒绝覆盖同名但字节不同的既有资产。

GitHub Actions builds the immutable `v1.0.1` tag commit with locked Rust 1.88 dependencies on six native targets, runs tests and CLI smoke tests, and only then aggregates release assets. Automation requires Cargo metadata and binary `--version` to match the tag, requires the complete six-asset matrix, and refuses to replace an existing same-named asset with different bytes.
