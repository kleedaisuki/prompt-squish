# v1.0.2 Target Layout and Clean Semantics

- Status: accepted and implemented
- Scope: user-visible project outputs, internal generation storage, dependency-cache hygiene, and the `clean` command
- Date: 2026-09-17
- Compatibility baseline: v1.0.1 project manifests, logical artifact locators, and inspect selectors

## 1. Decision summary

v1.0.2 must separate two models which the current implementation accidentally overlays:

1. the **product tree**, which contains paths a user declared or explicitly requested; and
2. the **generation repository**, which contains hashes, commit pointers, journals, and immutable
   recovery state.

The product tree stays at the configured workspace `target-dir` (default
`target/xmlsquish`) to preserve existing logical locators. It contains ordinary files at stable,
human-readable paths. Hashes and publisher internals move to the existing global, per-project
manager namespace. A project build therefore has this default visible shape:

```text
target/xmlsquish/
|-- prompt.prompt                         # default or declared output
|-- prompt.psdbg                          # only when debug output is requested
`-- ir/                                   # only when binary IR is requested
    `-- prompt/
        `-- semantic-example/
            |-- prompt.xsir
            `-- parts/
                |-- another.xsir
                `-- hello.xsir
```

It must **not** contain `.squish-publish`, target or generation hashes, a second
`target/xmlsquish` prefix, `*.xsmap`, or `*.build.json`. Those are implementation state, not
products.

`xmlsquish clean` has a deliberately small v1.0.2 contract:

```text
xmlsquish clean [--manifest-path PATH]
```

A normal clean removes the complete configured project target directory, retires that project's
private catalog/generation state, and prunes dependency-cache entries that are **provably
invalid**. It does not delete valid shared dependencies merely because the current project does
not reference them, and it does not clear the global CAS or action index. Global capacity/age
garbage collection is a separate future `cache prune` concern.

## 2. Problem definition and evidence

### 2.1 Object, scope, and assumptions

The research object is the state created by a project-mode invocation of the shipped executable.
The decision is intended to make the common workflow understandable without weakening content
addressing, cross-project reuse, crash recovery, inspection, or Windows support.

Assumptions:

- `workspace.target-dir` is a tool-owned, project-relative output root. The default remains
  `target/xmlsquish` in v1.0.2.
- The global manager and source-cache roots are disposable acceleration/state roots configured by
  `manager.storage-root` and `source.cache-root`.
- A lockfile and project sources are authoritative inputs. Neither the target tree nor a cache is
  an input to the correct clean-build result.
- Standard desktop filesystems do not offer a portable transaction spanning several arbitrary
  files and two storage roots. Recovery must therefore use an explicit journal and an ordinary
  next-invocation repair path.

### 2.2 Observed current flow

The following are repository observations, not conjecture:

This is not merely an unattractive name. The path proves that a project-relative logical locator

### 2.3 Desired decision properties

| Property | Required outcome |
|---|---|
| Human path | The reported locator names an ordinary file at that exact project-relative path. |
| Internal identity | Content and generation hashes remain available for integrity, reuse, recovery, and inspection, but only in private state. |
| Clean rebuild | Removing all derived state never changes the correct rebuilt bytes. |
| Compatibility | Existing manifests and default logical locators remain valid in a patch release. |
| Concurrency | Build, inspect recovery, and clean cannot race a project publication into a mixed authoritative state. |
| Cross-platform behavior | No correctness dependency on directory symlinks, hardlinks, Unix-only unlink semantics, or case-sensitive names. |

## 3. Chosen layout

### 3.1 Public product tree

The configured `target-dir` is the one public output root. Every public path is relative to that
root exactly once.

| Artifact role | Public path | Presence |
|---|---|---|
| Prompt | the manifest target `output`, default `<target>.prompt` | default build, or explicit `--emit prompt` |
| Debug bundle | prompt output with extension `.psdbg` | explicit `--emit debug` |
| Binary IR | `<output-parent>/ir/<output-stem>/<package>/<logical-source>.xsir` | explicit `--emit ir` |
| Static link map | none; CAS plus private generation manifest | always retained as required evidence |
| Target record | none; private generation/catalog state | always retained as required evidence |
| Build record | none in the target tree; private catalog plus inspect result | when finalization reaches the catalog |

The IR convention intentionally retains the v1.0.1 logical locator recipe. Its directories carry
semantic names—output, package, and source—not storage implementation identities. The manager
continues rejecting duplicate or case-folding-colliding output paths before execution.

An explicitly configured target root remains supported:

```toml
[workspace]
target-dir = "dist"

[target.chat]
entry = "src/chat.xml"
output = "agents/chat.prompt"
```

produces `dist/agents/chat.prompt`, not
`target/xmlsquish/.../artifacts/dist/agents/chat.prompt` and not a hard-coded
`target/xmlsquish` tree.

### 3.2 Private generation and catalog tree

The physical spelling is adapter-private, but ownership must be explicit:

```text
<manager.storage-root>/
|-- cas/                                  # globally shared immutable bytes
|-- actions.sqlite3                       # globally shared rebuildable action index
`-- catalog/projects/
    |-- .locks/                           # survives removal of a project catalog
    |   |-- <project-lock-id>.lock        # build/publish/clean coordination
    |   |-- <project-lock-id>.epoch       # supersedes pre-clean publisher instances
    |   `-- <project-lock-id>.clean.json  # redo-only clean journal
    `-- <canonical-project-id>/           # a hash is appropriate here, outside the project
        |-- target-publication-state/     # target generations and current pointers
        |-- build-catalog-state/          # catalog generations and current pointers
        `-- build-catalog-artifacts/      # private catalog projection
```

This diagram specifies ownership, not a stable user API. The existing
`catalog/projects/<project-id>` location may be reused or migrated internally. No public output,
event, inspect locator, or manifest is allowed to expose the private physical path.

The project ID continues to be derived from the canonical project root as documented in
`project-storage-namespaces.md`. Hashes solve collision and privacy problems in global internal
state; they solve no user problem inside a project's target directory.

### 3.3 Separate locator prefix from absolute output root

v1.0.2 preserves the established `PublicationPath` wire type while separating the two coordinate
systems in the storage layout:

```text
PublicationPath         = project-root-relative catalog identity
StorageLayout.prefix    = project-root-relative configured target-dir
artifact_relative(path) = validated path.strip_prefix(StorageLayout.prefix)
```

The publisher accepts only locators under the configured prefix and validates the equation

```text
project_root / locator == publication_root / artifact_relative(locator)
```

lexically and under the project's already validated path policy. Prompt, BinaryIr, and DebugInfo
are the closed public artifact kinds; Metadata and other manager records remain private. Callers
never strip one root and then prepend a different root.

## 4. Ownership and module boundaries

```text
typed CleanRequest / BuildRequest
              |
              v
        squish-manager
   plan, policy, ordered result
       /              \
      v                v
GenerationRepository  OutputMaterializer
(private authority)   (stable project files)
      ^                ^
      |                |
 squish-host composes concrete adapters
      |
      +---- SourceCacheCleaner (integrity-only prune)
```

| Component | Owns | Must not own |
|---|---|---|
| `squish-cli` | pure parsing of `clean` and `--manifest-path` | discovery, deletion, or cache scanning |
| `squish-protocol` | `CleanRequest`, `CleanResult`, operation kind, structured events | filesystem paths derived from configuration |
| root executable | project location, configuration loading, host composition, typed dispatch | recursive deletion or knowledge of cache subdirectories |
| `squish-manager::clean` | planning, operation ordering, cancellation boundaries, result aggregation | concrete `.squish-publish`, CAS, or fetch-cache paths |
| `squish-repository` | frozen project root and validated workspace target root | publisher journals or global cache policy |
| `squish-publish` | project publication lock, generation transaction, output projection, legacy generation reader, clean detach/recovery | source-cache integrity |
| `squish-fetch` | source-cache entry validation, per-entry/quarantine cleanup, acquisition/cleanup exclusion | target or build-catalog deletion |
| `squish-host` | concrete path authorization and composition of the preceding ports | command policy or terminal rendering |
| presentation | human/short/NDJSON rendering of structured facts | deciding whether deletion succeeded |

Adapter construction must remain lazy enough that locating a project or inspecting an absent
catalog does not create a target directory. In particular, the current `HostContext::new` creates
`v1/stage`, and the current publisher open creates state below its root; neither constructor
should be used as an incidental target-layout probe.

## 5. Build publication protocol

### 5.1 Normal build

For one successful target:

1. Build actions place verified immutable bytes in the global CAS.
2. The generation publisher validates the complete member set and stages a private generation
   manifest under the project's global namespace.
3. The output materializer writes every public member to a sibling temporary, verifies size and
   digest, flushes it, and records a durable project publication journal.
4. The journal records the commit decision only after all private and public candidates are
   complete.
5. Recovery or the current invocation advances the private current-generation pointer and
   atomically replaces each public file. The primary `.prompt` is replaced last. Parent
   directories are synchronized where the platform adapter supports that contract.
6. Internal members remain in CAS/private manifests. They are never copied into the target tree.
7. The manager finalizes the build catalog through its existing post-plan lifecycle.

The honest guarantee is:

- every individual public file replacement is atomic;
- after a successful command, the complete public set and private current generation agree;
- after process death, the next ordinary invocation rolls the decided transaction forward or
  rolls an undecided transaction back;
- an unrelated process reading several files during a crash window is not promised a
  cross-file atomic snapshot. Portable filesystems do not provide that transaction.

Inspect reads the authoritative private generation/CAS and verifies digests. Direct file reads
use the stable materialized paths. Both expose the same bytes after successful publication.

### 5.2 Why the primary prompt is last

The prompt is the consumer-facing product. Replacing it last means a normal successful
publication never advertises a new prompt before its requested companions have been written. It
does not turn several renames into an atomic filesystem transaction, so the journal and recovery
remain mandatory.

### 5.3 Concurrent builds

The per-project publication lock serializes only publication, recovery, and clean. Compilation
and CAS insertion remain concurrent and cross-project. When two builds reach publication:

- each already has a complete immutable candidate;
- the later lock holder re-reads the current generation before committing;
- identical generations reuse the current result;
- different generations commit in lock acquisition order; and
- catalog finalization records the actual committed generation, never a pre-lock assumption.

Because target publication and catalog finalization are separate lock acquisitions, each runtime
also freezes a project publication epoch. Clean advances that epoch immediately after its durable
journal decision and before detaching either root. Every publisher operation compares the frozen
epoch while holding the project lock; an older build is superseded instead of committing a catalog
after clean removed its target generation. A newly composed runtime freezes the advanced epoch and
can rebuild normally.

This preserves bounded build parallelism without permitting clean to remove an output tree while
a publisher is replacing its files.

## 6. `clean` contract

### 6.1 CLI and selection

```text
xmlsquish clean
xmlsquish clean --manifest-path path/to/xmlsquish.toml
```

The v1.0.2 command cleans the discovered workspace as one ownership unit. It intentionally does
not accept package, target, profile, or emit selection. The target root and catalog are shared,
and selective deletion would require persistent per-file ownership and catalog surgery. Adding
flags before those invariants exist would create special cases rather than useful functionality.

Clean is always network-free. It does not resolve a new dependency graph and does not modify
`xmlsquish.toml` or `xmlsquish.lock`.

### 6.2 Successful postconditions

After clean reports success:

1. the configured workspace target directory does not exist at its public path;
2. no target from the cleaned project is current in the private generation repository;
3. the project's build catalog is absent, so inspect cannot return a stale build as current;
4. source files, manifests, the lockfile, repository transaction state, and VCS files are
   unchanged;
5. the global CAS and action index are unchanged and may accelerate the next build;
6. valid shared registry/Git/materialized dependencies remain available; and
7. invalid dependency-cache entries found by the integrity pass are removed; busy entries are
   retained and counted rather than hidden.

The next build may therefore be warm with respect to global action/CAS data while still
re-materializing a clean public target tree. That is a feature, not a violation of clean.

The command is idempotent. Cleaning an already clean project succeeds and reports zero public
bytes removed, while still performing the invalid-cache maintenance pass.

### 6.3 What “invalid dependency” means

An entry is removable by ordinary `clean` only if validity is mechanically false:

| Class | Proof of invalidity | Action |
|---|---|---|
| Quarantine entry | It was already removed from the active namespace after failed complete validation. | Delete without following links. |
| Materialized tree | Marker missing/malformed, digest path mismatch, file set mismatch, byte length/hash mismatch, or manifest mismatch. | Take its digest lock, revalidate, then delete. |
| Registry materialization map | Mapping is malformed or names no completely verified materialized tree. | Remove the mapping; retain independently valid blobs. |

These are **not** invalid merely because the current lock does not reference them:

- another project may share them;
- an offline user may rely on them later;
- this repository has no complete registry of every project that uses the global cache; and
- absence from one graph is not proof of global unreachability.

Healthy global-cache reclamation requires leases or last-use metadata plus a retention policy.
That should become a separate `xmlsquish cache prune` operation. Cargo's current global cache GC
uses tracked last access and age thresholds; uv likewise separates `cache clean` from
`cache prune`. The project command must not pretend to have reachability evidence it lacks.

### 6.4 Clean transaction and recovery

The publication/clean lock and journal live outside the target directory, so deleting the target
does not delete the coordination mechanism being used.

```text
lock project
  -> recover prior publish/clean transaction
  -> write and sync redo-only Clean journal (commit decision)
  -> advance and sync publication epoch
  -> rename target root to a sibling tombstone (if present)
  -> rename private catalog/generation subtrees to private tombstones (if present)
  -> delete tombstones without following links/reparse points
  -> clear journal when physical reclamation completes
unlock project
```

All renames are within the same parent/filesystem. No namespace change occurs before the durable
journal decision; after it, recovery only rolls forward. If Windows denies rename or deletion
because an external process still has a handle open, the command returns a committed failure with
the facts completed so far, and the external journal lets the next ordinary host open resume the
same removal rather than asking the user to repair state.

Cancellation is honored before the durable decision. After the decision, cleanup is recovery
work: the manager emits cancellation-deferred evidence and finishes the bounded authoritative
transition. This follows the existing repository/publication lifecycle instead of inventing a
clean-only cancellation exception.

The dependency integrity pass takes the existing non-blocking per-digest materialization lock and
per-mapping update lock, then revalidates each candidate immediately before deletion. Busy entries
are retained and counted in `busy_dependency_entries`; this makes an active producer ordinary state
rather than a PID/mtime guessing special case. Physical deletion may continue after detachment because no
reader can newly discover the tombstone.

### 6.5 Future command surface

Two useful operations are deliberately outside v1.0.2:

- `clean --dry-run` can be added once the cleanup ports expose a strictly read-only planning path
  and tests prove that absent caches, catalogs, and target roots remain absent. Its estimates must
  be described as snapshots rather than deletion guarantees.
- `cache prune` can reclaim healthy but old global dependency/CAS/action entries once persistent
  last-use metadata, active leases, retention policy, and cross-project roots make reclamation
  defensible. Ordinary project `clean` must not approximate global reachability in the meantime.

## 7. Data model and invariants

### 7.1 Clean types

Conceptual protocol and port types are:

```text
CleanRequest {
    project: ProjectPath,
}

CleanPlan {
    project: CanonicalProjectIdentity,
    target_root: ValidatedTargetRoot,
    legacy_layout: Option<LegacyPublicationRoot>,
}

CleanResult {
    build_files: u64,
    build_bytes: u64,
    invalid_dependency_entries: u64,
    invalid_dependency_bytes: u64,
    busy_dependency_entries: u64,
}
```

The manager receives facts, not untyped directory paths. Human, short, and NDJSON renderers
therefore remain deterministic; a committed physical-clean failure retains the partial facts in
the result while the action and job remain failed.

### 7.2 Required invariants

1. **One coordinate system per type.** A target-relative path is never accepted where a
   project-relative locator is required.
2. **Exact locator.** A successful public artifact's locator names an ordinary file with the
   declared digest at `<project>/<locator>`.
3. **Private machinery.** Hashes, generations, journals, current pointers, link maps, and build
   records do not appear in the public target tree.
4. **Closed public kinds.** Only Prompt, BinaryIr, and DebugInfo artifacts are materialized;
   Metadata and other manager records remain private.
5. **No source overwrite.** The validated target root is project-relative, tool-owned, and does
   not overlap source/manifests; destinations cannot escape it.
6. **Deterministic membership.** Generation members and output paths are unique under the
   platform portability/case-folding policy and canonically ordered before hashing.
7. **Authoritative private generation.** Inspect and recovery use the generation manifest and
   CAS, never infer state by scanning target mtimes.
8. **Recoverable projection.** A decided publication or clean transaction is rolled forward;
   an undecided one is rolled back.
9. **Shared-cache preservation.** Ordinary project clean deletes no healthy shared source entry,
   CAS blob, or action record.
10. **Lease-respecting prune.** An entry cannot be detached while an acquisition/reader lease can
    expose it.
11. **Disposable acceleration.** Deleting target, project catalogs, source caches, CAS, or action
    index cannot change correct rebuilt bytes.
12. **No observation side effects.** Project location and inspect do not create missing
    target/cache/catalog directories.
13. **Idempotence.** Repeating clean after any successful clean or recovered clean is a no-op with
    a successful semantic result.
14. **Stable userspace.** Existing manifest syntax, default `target/xmlsquish/...` locators,
    artifact IDs/digests, source semantics, message modes, and exit conventions remain valid.

## 8. Compatibility and migration

### 8.1 What remains stable

- The default target root stays `target/xmlsquish`; changing it to `target` would be a cleaner
  greenfield convention but is inappropriate in a `1.0.2` patch.
- Explicit `[workspace].target-dir` and `[target.<name>].output` remain authoritative.
- Project-relative artifact locators remain the same; they become truthful filesystem paths.
- Artifact descriptors, digests, target generation identity, and inspect selectors remain typed
  contracts independent of the private physical layout.
- The lockfile and dependency selection semantics do not change.

### 8.2 Legacy `.squish-publish` state

v1.0.2 must recognize, but never produce, the v1.0.1 local generation layout.

1. **First v1.0.2 host open:** under the shared project lock, copy legacy generation state into a
   sibling staging directory in the private project catalog. A durable phase marker is written
   before the staged directory becomes authoritative.
2. **Validate before deletion:** recover journals, verify every current generation, and
   materialize its stable public projection. Only a fully validated private copy permits removal
   of the old `.squish-publish` tree.
3. **Crash recovery:** if a process dies after switching the private copy but before deleting the
   legacy tree, the phase marker makes the next open repeat validation and finish cleanup. A
   failed validation discards the private candidate but preserves the legacy authority for retry.
4. **Clean:** include the configured target root and recognized legacy publisher state in the
   same clean transaction. Since legacy state is below the target root, target detachment normally
   removes it in one operation.

The migration reader is a compatibility adapter with a removal horizon, not a second permanent
publisher.

### 8.3 Custom target directories

The current root binary hard-codes `target/xmlsquish` before the repository snapshot has loaded
the manifest. The replacement publisher must be opened lazily with a typed
`ValidatedTargetRoot` derived from that frozen snapshot, or receive the root in its publication
request. The host independently confines it to the canonical project root. A custom target root
must not require a second `ProductionHost` or a manager dependency on concrete storage.

## 9. Cross-platform and failure semantics

| Concern | Contract |
|---|---|
| Separators | Persist portable `/` logical paths; convert only in the platform adapter. |
| Case | Reject case-folding collisions before writes, including sibling temporary/tombstone names. |
| Windows reserved names | Reuse the publisher's portable-segment policy. |
| Long paths | Use the existing normalized native path adapter; never lengthen public paths with hashes. |
| Symlink/junction root | Treat the configured target root as one directory entry during detach; never recursively follow links discovered inside a tombstone. |
| Cross-volume rename | Staging/tombstones are siblings of their destination, so the normal protocol never requests it. |
| Open Windows handles | Bounded retry for transient sharing violations; otherwise retain the external journal/tombstone, return committed failure, and retry during recovery. |
| Missing paths | Ordinary idempotent absence, not an error. |
| Malformed journal | Preserve it for diagnostics and return a structured adapter error; do not guess or recursively delete an unvalidated path. |
| Partial cache corruption | Detach only after type/path/integrity validation; a miss remains rebuildable. |

Research cautions against assuming that a sequence of `rename` and `fsync` calls has identical
persistence behavior on every filesystem. The OSDI study *All File Systems Are Not Created Equal*
found that application protocols depend on filesystem-specific persistence properties and found
crash vulnerabilities in production systems. The practical response here is a small explicit
state machine, recovery tests seeded at both sides of the commit decision, and no claim of
portable multi-file atomic visibility. Real process-death injection for the new clean boundaries
remains future test infrastructure.

## 10. CLI and dispatch integration

Adding the command requires one exhaustive route rather than an out-of-band deletion helper:

1. Add `CleanRequest`, `CleanResult`, `OperationKind::Clean`, and `OperationRequest::Clean` in
   `squish-protocol`.
2. Add `Command::Clean(CleanArgs)` and help/examples in `squish-cli`; parser tests must cover exact
   argv, JSON bootstrap errors, and rejection of unsupported selection flags.
3. Extend root `requested_project`, `set_project`, query classification, and composition without
   introducing a clean-specific discovery algorithm.
4. Add `squish-manager/src/clean.rs`; manager dispatch returns structured lifecycle events and an
   `OperationResult::Clean`.
5. Add manager-owned cleanup ports. Production `squish-host` composes publication/catalog cleanup
   with `squish-publish` and source integrity cleanup with `squish-fetch`.
6. Extend presentation for human, short, quiet, and NDJSON modes. Stable machine output reports
   removed build files/bytes, invalid dependency entries/bytes, and busy skipped entries.

Clean uses the manager's existing planning/finalization vocabulary where it is truthful and does
not manufacture cacheable transform actions for deletion. One typed, non-cacheable Clean write
action invokes the host's project transaction and dependency-cache integrity maintenance; the host
returns their independently counted facts in one result.

## 11. Implementation slices and order

| Slice | Owner boundary | Deliverable | Depends on |
|---|---|---|---|
| 1. Path split | manager storage + publish | `StorageLayout.publication_prefix` is distinct from the absolute publication root; publisher validates and strips it exactly once | none |
| 2. Private generations | publish + host | target generation repository below global project namespace, preserving current recovery tests | 1 |
| 3. Stable projection | publish + manager build | direct ordinary files at existing locators; internal artifacts not materialized | 1, 2 |
| 4. Legacy migration | publish + host | read-only old layout, first-success cutover, no new local generations | 2, 3 |
| 5. Typed clean surface | protocol + CLI + root + manager | parse/dispatch/results with no selection special cases | none; can proceed alongside 1-4 |
| 6. Project clean transaction | publish + host | lock/journal/detach/recover target and project-private state | 2, 5 |
| 7. Invalid dependency prune | fetch + host | per-entry try-locks, complete-marker validators, no-follow deletion, facts | 5 |
| 8. Presentation/docs | presentation + root docs | human/short/NDJSON output, root `SKILL.md`, README/changelog | 3, 5-7 |
| 9. Release gates | process/recovery/CI | migration, clean, and exact-layout smoke on Linux/macOS/Windows | all |

Slices 2 and 3 should land together from a userspace perspective: no released intermediate build
may stop producing inspectable current artifacts. Slice 5 can be developed independently against
fake ports. Each slice should preserve exhaustive enum matches so missing routing fails at compile
time.

### 12.1 Unit and component tests

### 12.2 Manager and repository integration

| Scenario | Required observation |
|---|---|
| Default single target | physical `target/xmlsquish/prompt.prompt` equals reported locator and digest |
| Custom target root/output subdirectory | only configured root/path appears; no hard-coded default tree |
| Prompt/debug/IR emit combinations | only requested public companions appear; link/build metadata remains inspectable but absent from target |
| Workspace with same target names | package-qualified generation identities remain unambiguous; declared public outputs must still be collision-free |
| Warm build after clean | target is reconstructed byte-identically; CAS/action hits are permitted and reported truthfully |
| Invalid dependency plus offline build | clean removes invalid entry; subsequent frozen/offline build is an honest cache miss, never stale bytes |
| Two projects sharing one dependency | cleaning either project retains the healthy shared materialization and the other project builds offline |
| Concurrent build/build | both complete; last committed generation and public prompt agree |
| Concurrent build/clean | shared project lock serializes publication/detach; final state is one whole build or one whole clean, never mixed |
| Concurrent clean/clean | both succeed idempotently; no double-delete error |

### 12.3 Migration process tests

1. Seed the exact v1.0.1 local generation shape, then run v1.0.2 `inspect artifact`; bytes and
   digest remain available.
2. Seed v1.0.1, perform a successful v1.0.2 build, and assert stable direct files plus absence of
   `.squish-publish` and hash directories.
3. Seed v1.0.1, make the new source invalid, and assert a failing build does not destroy the last
   inspectable legacy generation.
4. Seed v1.0.1, run clean, and assert the entire configured target root and stale project catalog
   are absent.

### 12.4 Recovery tests

v1.0.2 acceptance must exercise the implemented clean recovery API and persistent state machine
without claiming new process fault selectors. Component and process-level fixtures should seed
each durable state directly, invoke an ordinary public command, and require the following
convergence:

| Seeded durable state | Ordinary follow-up | Required state |
|---|---|---|
| publication candidates staged, no decision | inspect/build | previous generation and public prompt |
| publication commit decided | inspect/build | new generation and direct prompt rolled forward |
| clean journal absent | build/inspect | current target/catalog remain authoritative |
| clean journal durable, one or both roots present | build/inspect | redo recovery detaches and removes both roots |
| clean journal durable, tombstones present | build/inspect | redo recovery removes tombstones and clears journal |
| dependency entry detached | clean/build | active namespace has no invalid entry; retry completes tombstone deletion |

Fixtures perform no manual repair and live under the repository `.temp`, consistent with existing
policy. Adding real child-process termination selectors for these boundaries is valuable future
fault-injection work, but is not part of the v1.0.2 public or acceptance contract.

### 12.5 Supported-desktop release smoke

On Linux, macOS, and Windows:

1. create a fresh project;
2. build prompt + IR + debug;
3. assert the prompt is an ordinary file at the reported locator;
4. assert there is no `.squish-publish`, no 64-hex path component below the target root, no
   duplicated `target/xmlsquish`, and no `.xsmap`/`.build.json` public file;
5. inspect prompt/link/build evidence;
6. run `clean` and prove the configured target root is absent;
7. build again offline/frozen where fixtures permit and compare public bytes;
8. run clean again and require success.

## 13. Alternatives rejected

### 13.1 Only strip `target/xmlsquish` before calling the current publisher

Rejected. It fixes the duplicated prefix but leaves target/generation hashes and internal
manifests in the public output root. It treats a data-model error as a string manipulation bug.

### 13.2 Keep generations in target and add friendly copies or symlinks

Rejected. Copies double storage and can drift; symlinks make cache deletion and Windows behavior
part of the user contract. Bazel uses convenience symlinks while keeping complex state outside
the workspace, but prompt-squish already has cheap direct CAS-to-file materialization and should
not require link support.

### 13.3 Change the default output root to `target`

Rejected for v1.0.2. It is attractive for a new major version but changes documented locators and
scripts without being necessary to remove hashes or nesting.

### 13.4 Directory-swap the entire target root for every target build

Rejected. Independent targets share the root, keep-going builds may publish only a subset, and an
entire-root swap would erase untouched successful outputs. Per-target recoverable projection is
the normal case.

### 13.5 Delete every dependency not in the current lock

Rejected. The cache is global and shared, while the current project lock is only one reachability
root. This would break another project's offline build and violate the cache's ownership model.

### 13.6 Make clean a root-binary `remove_dir_all`

Rejected. It bypasses typed dispatch, custom target roots, publication locks, catalog coherence,
legacy recovery, structured output, cancellation, and fault-injection tests.

## 14. Risks, unknowns, and falsification

| Risk | Current judgment | Evidence that would revise it |
|---|---|---|
| Direct files weaken current generation atomicity | Individual files are atomic; v1.0.1 never materialized the documented locator directly, while v1.0.2 uses a journaled projection. This is a net product improvement, but not a multi-file transaction. | A supported consumer demonstrably requires externally atomic prompt+debug reads; then publish a single container or versioned directory plus an explicit accessor instead of claiming the filesystem can do it. |
| Global project state becomes larger | Generation manifests are small and blobs already reside in CAS; duplicate target-tree copies disappear. | Measurements show private manifest growth dominates; add retention rooted in current catalogs and active leases. |
| Clean blocks on a long build | Publication lock is short-lived; source maintenance can wait on acquisition leases. | Profiling shows unacceptable tail latency; change invalid-cache prune to opportunistic per-entry try-locks while retaining deterministic target cleanup. |
| Windows deletion is delayed by open handles | The command returns a committed failure and the next host open retries from the journal. | Real CI/local evidence shows tombstones accumulate; add bounded background retirement and explicit deferred-byte statistics before broadening cleanup scope. |
| Legacy adapter becomes permanent | It is necessary for userspace preservation but increases test burden. | Once an announced compatibility window and migration telemetry show no legacy state, remove it in a major/minor release, not silently in a patch. |
| Invalid-cache scan is expensive | Integrity verification is bounded by existing fetch limits but may read many bytes. | Benchmarks exceed the clean latency budget; persist verified health/access metadata, sample unchanged entries, and keep full verification available without deleting unverified healthy entries. |

This design is falsified if any supported-platform acceptance run observes: a reported artifact
locator without a matching ordinary file after successful build; a hash/internal file in the
target tree; a successful clean leaving the configured target root current; loss of a healthy
shared dependency; a build/clean race producing mixed authoritative state; or an ordinary
follow-up unable to recover a persisted clean/publication state represented in the recovery test
matrix.

## 15. External evidence and transfer judgment

These sources are evidence for patterns, not proof that their complete designs fit prompt-squish:

- Cargo documents that plain [`cargo clean`](https://doc.rust-lang.org/cargo/commands/cargo-clean.html)
  removes the entire target directory, while its global cache GC separately uses last-access and
  age information. **Adopt:** a simple whole-output-root default and evidence-based shared-cache
  reclamation. **Do not copy yet:** package/profile-selective clean without corresponding output
  ownership metadata.
- Gradle's Base plugin defines `clean` as deleting the configured build directory, and keeps its
  local build cache separate from the project build directory
  ([Base plugin](https://docs.gradle.org/current/userguide/base_plugin.html),
  [build cache](https://docs.gradle.org/current/userguide/part6_gradle_caching.html)). **Adopt:**
  clean outputs without pretending a reusable cache must also be cold.
- uv documents separate `cache clean` and `cache prune` operations, uses concurrency control for
  cache-modifying operations, and treats centralized cached environments as recreatable
  ([uv caching](https://docs.astral.sh/uv/concepts/cache/)). **Adopt:** explicit maintenance
  ownership and no direct user modification of cache internals.
- npm describes its cache as opaque, content-addressed, integrity-verified, and disposable; its
  `verify` operation garbage-collects unnecessary data
  ([npm cache](https://docs.npmjs.com/cli/v7/commands/npm-cache/)). **Adopt:** exact-byte cache
  guarantees and self-healing corruption, not cache layout as userspace.
- Bazel deliberately keeps hashed workspace state under a global output root and exposes easier
  convenience paths in the workspace
  ([output directory layout](https://docs.bazel.build/versions/main/output_directories.html)).
  **Adopt:** hashes belong in private global state. **Reject here:** convenience symlinks because
  they complicate Windows and cache lifecycle without buying meaningful performance for prompt
  files.
- Pillai et al., *All File Systems Are Not Created Equal: On the Complexity of Crafting
  Crash-Consistent Applications*, OSDI 2014, found filesystem-dependent persistence properties
  and crash vulnerabilities across mature systems
  ([paper](https://www.usenix.org/conference/osdi14/technical-sessions/presentation/pillai)).
  **Adopt:** explicit crash-state partitions and recovery tests for persisted intermediate states;
  add real process-death injection when the corresponding selectors exist. **Do not claim:** that
  `rename` alone provides a portable multi-file durable transaction.
- FSCQ's Crash Hoare Logic makes crash conditions and recovery procedures part of the
  specification
  ([SOSP 2015 paper](https://adam.chlipala.net/papers/FscqSOSP15/)). Formal verification is not a
  v1.0.2 dependency, but its framing is directly useful: every durable boundary above states both
  the crash state and recovery rule, which keeps future verification possible.

The common production lesson is not “copy Cargo/Bazel/uv.” It is that user-facing products,
project-private state, and globally shared caches have different ownership and cleanup rules.
The current layout is difficult because those distinctions were erased. Restoring them removes
the special cases instead of adding one more condition around a hash directory.
