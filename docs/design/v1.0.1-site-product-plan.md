# xmlsquish v1.0.1 Website Product Plan

- **Status:** implementation-ready product specification
- **Decision date:** 2026-09-16
- **Surfaces:** `xmlsquish.moesegfault.dev`, Simplified Chinese and English
- **Primary routes:** `/`, `/en/`, `/releases/`, `/en/releases/`, `/ns`, `/en/ns/`
- **Release:** `v1.0.1`

## 1. Product decision

The website will become one small product surface with three first-class destinations:

1. **Home** explains why xmlsquish exists and demonstrates the product.
2. **Release log** explains what changed, how to get the latest version, and what a user must do next.
3. **XML namespace** makes the stable namespace identity and vocabulary explorable without turning the site into a documentation portal.

All three destinations must use the current home page's visual language: warm cream surfaces, coral accent, large editorial headings, compact monospace eyebrows, bordered cards, dark code panels, generous spacing, and the existing light/dark theme behavior. The home page's hero, section order, two-column demonstrations, and overall rhythm are preservation constraints. This is a redesign of the other surfaces and the shared shell, not a home-page rebrand.

The site must **not** present a generic documentation shell. There is no docs sidebar, tree navigation, breadcrumb stack, table-of-contents rail, or Markdown-looking article as the primary experience. Raw specifications remain available as linked resources, while human routes remain designed product interfaces.

### 2.2 External product patterns

These are reference patterns, not templates to copy literally:

| Product | Useful pattern | What xmlsquish should adopt | What not to copy |
| --- | --- | --- | --- |
| [Bun home](https://bun.com/) and [Bun blog/releases](https://bun.com/blog) | The home page exposes the latest release as a product update with a version, date, summary, upgrade command, and route to all releases. | Make v1.0.1 visible from the existing home shell, and make the release log answer “what changed?” and “how do I get it?” immediately. | Do not add Bun's broader ecosystem navigation or content volume. |
| [Bun reference](https://bun.com/reference) | Reference is browse/search-oriented and grouped by product concepts rather than rendered as a long introductory document. | Make the eleven namespace directives searchable and grouped; keep raw specification links secondary. | Do not build symbol-detail routing, generated API chrome, or a docs hierarchy for eleven items. |
| [Resend changelog](https://resend.com/changelog) | Dated, visual, outcome-led release cards feel like a continuing product story. | Use reverse-chronological release entries, scannable change groups, and a strong latest-release card. | Do not add subscriptions, screenshots, or filters before there is enough release volume. |
| [Linear changelog](https://linear.app/changelog) | Major launches lead with narrative outcomes; smaller fixes and API changes are grouped beneath them. | Separate v1.0.1 highlights from grouped technical changes and previous releases. | Do not reproduce its dense category system or publication machinery. |

Accessibility constrains the requested underline-free interaction. W3C technique [G183](https://www.w3.org/WAI/WCAG22/Techniques/general/G183) requires sufficient link-to-text contrast and an additional visual cue on hover/focus when color is the only resting cue. The site should therefore use the home page's accent wash, weight, arrow/badge, border, and focus ring instead of adding an underline. Mobile behavior must follow [WCAG reflow guidance](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), and controls must meet at least the [24 by 24 CSS pixel target-size minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum).

## 3. Users and jobs

| User | Immediate question | Required path |
| --- | --- | --- |
| Evaluating developer | “What does xmlsquish do, and why is it different from concatenating XML?” | Land on Home, understand project/build/artifact value, inspect the live build model, then continue to source or release. |
| Returning user | “What changed in v1.0.1, and should I upgrade?” | Open Release log, scan highlights and change groups, see migration impact, then download or install. |
| New adopter | “How do I install the right binary and verify it?” | Open the latest release, choose OS/architecture, find SHA-256 information and limitations without reading an essay. |
| XML author | “What exact namespace URI do I use, and which directives exist?” | Open Namespace, copy the exact URI, inspect a minimal example, browse or filter directives, then reach the full specification if needed. |
| Tool/automation author | “Where is stable machine-readable release and language information?” | Discover versioned release JSON, raw DSL Markdown, canonical/hreflang metadata, and immutable historical snapshots. |

The primary decision purpose is task completion, not page-view maximization. A successful design gets each user to the next concrete action with minimal navigation and no ambiguity about version or namespace identity.

### Global navigation

The same header and footer appear on every human page.

- Primary labels: **Home / Release log / XML namespace** and **首页 / 发布记录 / XML 命名空间**.
- The logo always returns to the current locale's home page.
- The current destination has `aria-current="page"` and a persistent accent-wash/pill treatment; active state is not communicated by color alone.
- Language switching preserves the current page type rather than returning to Home.
- Theme and GitHub actions retain their current function.
- Home-section anchors such as Build, Model, and CLI remain discoverable through home-page CTAs and content. They do not crowd the global navigation.
- At narrow widths, the product links move into a real keyboard-operable menu or a second reflowed row; they must never simply disappear as they do in the current home CSS below 800 px.

### Cross-surface flow

```text

  ◀──────────── logo / Home ───────────── previous/current release┘
```

Each page owns a distinct question. Cross-links should move the user forward, not duplicate whole sections across routes.

## 5. Page behavior and content hierarchy

### 5.1 Home: preserve, connect, and update

**Hard preservation contract**

- Preserve the current hero's two-column composition, large editorial headline, build graph, primary/secondary CTAs, and spacing.
- Preserve the current major section sequence: journey, build explorer, language model, capabilities, CLI, artifact metrics, limitations, and closing CTA.
- Preserve the current palette, typography scale, code-panel treatment, card geometry, page width, theme behavior, and overall desktop/mobile rhythm.
- Do not replace the home page with a release feed, docs landing page, dashboard, or generic feature-card grid.

**Allowed integration changes**

- Replace the current page-local header with the unified global header while retaining its height, brand block, sticky behavior, and visual tokens.
- Update the hero revision/version cue to v1.0.1 and make it a highlighted route to the Release log.
- Add compact Release log and Namespace destinations to the existing closing/CTA region; do not insert a new long section that changes the home narrative.
- Apply the unified underline-free link language to all home links, including current `.text-link` elements.
- Update product metadata from 1.0.0 to 1.0.1 from the same release data that feeds the Release log.

The home page remains the product story. It should mention the latest version, but it must not reproduce release notes or the namespace catalog.

### 5.2 Release log: a product update surface

The Release log replaces the current second launch page. Its content order is:

1. **Latest-release hero**
   - `v1.0.1`, publication date, stable status, outcome-led headline, and a two- or three-sentence summary.
   - Primary CTA: download/install v1.0.1.
   - Secondary CTA: GitHub Release.
   - Compact “upgrade impact” label: for example, no migration required / review migration notes.
2. **Acquisition panel**
   - Platform cards for Windows, Linux, and macOS, with architecture and minimum-platform labels.
   - Tagged source-install command and copy action.
   - SHA-256 manifest and factual signing/notarization boundary.
3. **What changed in v1.0.1**
   - At most three outcome-led highlight cards.
   - Detailed entries grouped under user-recognizable headings such as **Build and runtime**, **Artifacts and inspection**, and **Reliability and maintenance**.
   - Each entry begins with the observable user effect. Internal crate names and refactor mechanics may follow only when they help operators or integrators.
4. **Compatibility and action**
   - Explicit migration requirement, supported platforms/toolchain, known limitations, and the exact next command.
   - Omit empty sections; never show a heading with “none” as filler.
5. **Previous releases**
   - Reverse-chronological cards with version, date, two-line summary, status, and stable anchor (for example `#v1-0-0`).
   - v1.0.0 remains discoverable without repeating its former full product-launch page. Link to the immutable GitHub Release and versioned JSON.

The current six-command journey, product-model education, and broad feature explanation belong on Home and should be removed from the Release log. Release content is not a commit dump: conventional-commit prefixes, issue numbers, and architecture vocabulary are supporting details, not headings.

**Release content contract**

One typed release record must drive the latest-version badge, visible Release log, download URLs, source-install command, JSON-LD, and versioned JSON artifact. Required fields are:

```text
version, tag, date, status, headline, summary,
upgradeImpact, changeGroups[], platforms[],
githubRelease, checksums, sourceInstall, limitations[]
```

This is a product requirement, not a prescribed framework. The implementation may replace the current components and data layout entirely. The important invariant is that users cannot see v1.0.1 in one surface and stale v1.0.0 assets or metadata in another.

### 5.3 XML namespace: a compact explorer

The exact namespace remains:

```text
https://xmlsquish.moesegfault.dev/ns
```

It must never gain a trailing slash or release suffix. The localized English page is a description of the same namespace, not a second namespace identity.

Content order:

1. **Namespace hero and identity card**
   - Outcome-led headline, stable-status badge, exact selectable URI, and Copy URI button.
   - Copy is progressive enhancement: if JavaScript is unavailable, the URI remains visible and selectable and no dead copy control is shown.
2. **Use it now**
   - One minimal `xs:entry` example in the home page's dark code-panel style.
   - One short explanation that the URI identifies vocabulary and is not fetched during builds.
3. **Vocabulary explorer**
   - Show all eleven directives, grouped by task rather than as one flat table:
     - **Document roots:** `module`, `entry`
     - **Definitions and composition:** `import`, `macro`, `param`, `expand`
     - **Values and content:** `arg`, `fill`, `slot`, `insert`
     - **Control:** `ifr`
   - Each directive is a card with element name, kind/group badge, one-sentence contract, and stable fragment anchor.
   - An enhanced search field filters names and contracts. Without JavaScript, the search UI is absent and all cards remain visible.
   - Eleven items do not justify separate detail pages, pagination, or a docs sidebar.
4. **Build boundary visualization**
   - Reuse the home page's pipeline language to show `XML → XSIR → link → .prompt (+ .xsir/.psdbg)`.
   - Explain cross-file validation and why XSD alone is not the product contract in no more than two compact blocks.
5. **Resources and version policy**
   - Product-style resource cards for current specification, runnable examples, release/migration log, immutable v0.3.0 and v0.2.0 snapshots, license, and standards basis.
   - Clearly distinguish **product version**, **specification snapshot**, and **namespace identity**. Do not suggest that v1.0.1 changes the namespace URI.

This route is a product catalog for human users. The full DSL specification remains a raw linked artifact at `/ns/dsl.md`; it is not rendered into the primary page.

## 6. Visual and interaction language

### Shared tokens and structure

- Continue using MoeSegfault Style and the existing `--moe-*` / `--xs-*` tokens.
- Use the home page's `page-width`/`--xs-max`, bordered cards, warm surface bands, coral wash, dark code surfaces, and monospace eyebrows.
- Use one shared header/footer component and shared primitives for buttons, links, badges, cards, code panels, and section headings. Page components own only their distinct compositions.
- Keep line lengths readable: prose about 60–75 characters; wider space is reserved for cards, vocabulary grids, and release assets.

### Underline-free links

No human product page uses underlines for links at rest, hover, focus, visited, or active states. This includes header, footer, body links, resource links, and legal links.

| Link type | Resting cue | Hover cue | Focus cue |
| --- | --- | --- | --- |
| Global navigation | Semibold label with padded hit area | Coral accent wash and stronger text | Existing 3 px high-contrast outline plus wash |
| Current route | Persistent rounded accent wash, stronger weight, `aria-current` | Slightly stronger wash | Outline remains visible outside the pill |
| Inline/product action | Accent text, semibold weight, persistent arrow or resource-type badge | Background highlight expands/intensifies; arrow may shift by at most 2 px | 3 px outline and persistent background highlight |
| Card link | Border, title weight, and arrow/icon make the whole affordance recognizable | Accent border, shallow shadow, optional 1–2 px lift | 3 px outline around the card, no lift required |
| Primary/secondary button | Existing filled or bordered button geometry | Existing brightness/lift treatment | 3 px outline with sufficient separation |

For inline prose where an arrow/badge would be noisy, place the link in a small action cluster or resource card instead of falling back to color-only text. Motion is enhancement only and is disabled under `prefers-reduced-motion`.

## 7. Responsive, no-JavaScript, and accessibility behavior

### Breakpoints and reflow

- **Wide (>= 1050 px):** full horizontal product navigation; release hero and namespace hero may use two columns; three-column card grids are allowed.
- **Medium (641–1049 px):** hero/grid columns collapse when content would become cramped; global navigation remains reachable and does not overflow.
- **Small (320–640 px):** single-column content; full-width download actions and search; code panels may scroll internally; global menu contains Home, Release log, Namespace, language, theme, and GitHub actions as needed.
- No document-level horizontal overflow at 320, 390, 768, or 1440 CSS px. Long namespace URIs, hashes, commands, and asset names wrap or scroll only inside their bounded component.

### Accessibility contract

- One `h1` per page, ordered heading hierarchy, and `header`, `nav`, `main`, `section`, and `footer` landmarks.
- A skip link targets `#main` on every route.
- All destinations remain reachable by keyboard with JavaScript disabled.
- Visible focus uses the existing 3 px accent outline with at least 4 px offset where geometry permits; it is never replaced by color alone.
- All pointer targets are at least 24 by 24 CSS px; primary navigation and buttons target 44 px height where practical.
- Normal text meets 4.5:1 contrast; large text and UI boundaries meet 3:1. Underline-free inline links additionally meet at least 3:1 against surrounding text or use a persistent non-color cue.
- Active navigation includes `aria-current="page"`. Icon-only controls have localized accessible names. Decorative arrows/icons are hidden from assistive technology.
- Copy confirmation uses a polite live region and does not steal focus. Copy failure leaves the selectable value intact and offers no blocking error state.
- Search results announce their count; Escape clears search only when the search field owns focus. With JavaScript disabled, all namespace items are present.
- Theme choice respects system preference and continues to work when storage is unavailable. Nonessential motion honors `prefers-reduced-motion`.
- Chinese and English pages are monolingual except proper nouns, commands, file names, and necessary technical identifiers.

## 8. Metadata, discovery, and publication truth

- Canonical and reciprocal `hreflang` links remain page-specific; `x-default` remains Simplified Chinese.
- Home `SoftwareApplication` metadata reports `1.0.1`.
- The Release log owns exactly one truthful latest-release `SoftwareApplication` entity; it reports v1.0.1 and only published, reachable asset URLs.
- `/releases/1.0.1.json` is added as the current machine-readable release record; `/releases/1.0.0.json` remains an immutable historical record.
- The Release log's `rel="alternate" type="application/json"` points to v1.0.1. Namespace keeps `rel="describedby"` to `/ns/dsl.md`.
- Sitemap and `llms.txt` identify v1.0.1 as latest without erasing historical resources.
- The site must not claim that a GitHub Release, asset, checksum file, signature, or notarization exists until publication checks observe it.
- Social cards, visible version copy, JSON-LD, JSON records, install commands, tags, and asset filenames must agree.

## 9. Failure and edge behavior

| Condition | Required user behavior |
| --- | --- |
| JavaScript blocked | All page content, global destinations, downloads, raw resources, vocabulary cards, and the visible URI remain usable; copy/search enhancements disappear cleanly. |
| Local storage blocked | Theme falls back to system preference; control remains operable without page errors. |
| Copy API unavailable or denied | URI/command remains selected or selectable; show a brief nonblocking localized message. |
| Long translated text or asset name | Card grows vertically; content does not overlap or create page-level horizontal scroll. |
| Release asset not yet public | Do not present an enabled download or “published” status. Publication must be completed before the page advertises availability. |
| No matching namespace search result | Show a localized empty state, the query, result count zero, and one Clear action; do not hide the resource/version section. |
| Deep link to a directive or release | The anchored card/entry receives scroll margin below the sticky header and a transient/persistent highlight that is not color-only. |
| Unsupported narrow viewport | Product navigation and primary actions reflow; only bounded code/technical values may scroll horizontally. |

## 10. Explicit non-goals

- No general-purpose documentation portal, docs route, docs sidebar, breadcrumb hierarchy, or site-wide documentation search.
- No blog, newsletter, account system, analytics requirement, or user-generated content.
- No separate detail route for each of the eleven XML directives.
- No release filters, tags, pagination, or subscription UI until release volume creates a demonstrated need.
- No animation framework or new visual-design dependency.
- No change to the namespace URI and no version number embedded in that URI.
- No translation of the full Simplified-Chinese DSL specification as part of this release; the English product page must label that resource accurately.
- No attempt to preserve the current `ReferenceLayout` implementation or its CSS. Preserve public behavior and stable URLs, not internal structure.
- No fabricated popularity, performance, security, compatibility, signing, or durability claims.

## 12. Concrete implementation boundaries

The implementation may rename files, but it should preserve these ownership boundaries so that a
future release cannot recreate the current split design accidentally.

| Boundary | Owns | Must not own |
| --- | --- | --- |
| `BaseLayout` | Document metadata, canonical/hreflang links, theme bootstrap, external style loading, skip link, and global design tokens. | Page-specific header/footer markup, release copy, or namespace vocabulary. |
| `ProductShell` (new shared layout) | Shared site header, mobile navigation, footer, page-width contract, current-route state, locale/theme/GitHub actions. | Home sections, release chronology, or namespace cards. |
| `SiteHeader` / `SiteFooter` | One semantic implementation rendered by Home, Release log, and Namespace. | Page metadata or page-specific content. |
| Shared interaction stylesheet/primitives | Underline-free link states, buttons, action links, cards, badges, code panels, headings, focus/reduced-motion rules. | One-off selectors tied to a particular release number. |
| `LandingPage` | Existing home composition and its compact v1.0.1/namespace gateways. | Full release notes or a namespace directive catalog. |
| `ReleaseLogPage` | Latest-release hero, acquisition, grouped changes, compatibility/action, previous-release list. | Generic product education already present on Home. |
| `NamespaceExplorerPage` | Namespace identity, minimal example, search enhancement, grouped directive cards, validation pipeline, resources/version policy. | The full Markdown DSL specification or general docs navigation. |
| Release data module | Typed release records and helpers used by HTML, JSON/JSON-LD generation, asset URLs, Home version cue, and tests. | Handwritten component markup or visual styles. |
| Namespace data module | The eleven directive records, groups, stable anchors, localized summaries, and resource records. | Search UI state or page layout. |
| Enhancement islands/scripts | Theme, mobile-menu enhancement if needed, copy feedback, and namespace filtering. | Hiding essential static content before hydration or making navigation depend on client JavaScript. |

`ReferenceLayout` should be retired rather than restyled into a second shell. `ThemeControl` and the
existing build explorer remain reusable. The six localized page entry files stay thin: they select a
locale and render the corresponding product page inside the shared shell.

Recommended source-level split:

```text
site/src/
├── layouts/
│   ├── BaseLayout.astro
│   └── ProductShell.astro
├── components/
│   ├── SiteHeader.astro
│   ├── SiteFooter.astro
│   ├── LandingPage.astro
│   ├── ReleaseLogPage.astro
│   ├── NamespaceExplorerPage.astro
│   └── product/                 # shared visual primitives only
├── data/
│   ├── releases.ts             # latest + history, one factual source
│   └── namespace.ts            # groups + eleven directive records
├── i18n/
│   ├── messages.ts
│   └── routes.ts
└── pages/                       # locale wrappers and machine endpoints
```

This is a responsibility map, not a requirement to create a component for every visual fragment.
Prefer a few cohesive components over a large “design system” abstraction. In particular, do not
create a generic documentation renderer to serve one namespace catalog.

### Test ownership

- Shell/navigation tests cover all three pages, both locales, active route, mobile menu, theme,
  keyboard focus, no-JavaScript access, and link styling.
- Home tests retain the existing build-explorer and content-evidence assertions.
- Release tests consume the same release data and verify HTML, JSON-LD, versioned JSON, install
  commands, and asset URLs as one contract.
- Namespace tests verify exact URI identity, unique eleven-item coverage, grouping, filtering,
  stable anchors, raw current spec, and immutable historical snapshot hashes.
- Responsive tests exercise 320, 390, 768, and 1440 px in both themes. They must diagnose the
  overflowing component rather than masking it with `overflow-x: hidden` on the document.

## 13. Acceptance scenarios

The following scenarios are the completion contract.

### A. One coherent product

1. **Given** any Chinese or English human route, **when** the page loads, **then** it shows the same branded header/footer structure and exposes Home, Release log, and XML namespace.
2. **Given** the current page, **then** exactly one global destination has `aria-current="page"`, a persistent non-color visual state, and the correct locale-preserving URL.
3. **Given** a 390 px viewport with JavaScript disabled, **when** the header is used by keyboard, **then** all three destinations and language switching remain reachable.
4. **Given** navigation among all three destinations, **then** the user never enters a docs sidebar/article shell or loses theme/language controls.

### B. Home preservation

1. The hero remains a two-column copy/build-graph composition on desktop and one column on mobile.
2. Journey, build explorer, language model, capabilities, CLI, metrics, limitations, and closing CTA remain in their current order.
3. Existing interactive build-explorer scenarios and no-JavaScript fallback continue to pass.
4. The visible latest version and structured product version are `1.0.1`, and the version cue reaches the Release log.
5. No new full-length release or namespace section is inserted into the home narrative.

### C. Release log

1. The first visible release is v1.0.1 with its actual publication date, stable status, outcome summary, upgrade impact, and working GitHub Release link.
2. Every enabled native download resolves to the exact v1.0.1 GitHub asset; SHA-256 and source-install links agree with the version/tag.
3. Changes are grouped by observable product area; the page does not reproduce the six-command home journey.
4. v1.0.0 appears after v1.0.1 with an immutable anchor, date, summary, GitHub link, and JSON link.
5. Visible content, JSON-LD, `/releases/1.0.1.json`, Home metadata, social metadata, sitemap, and `llms.txt` agree on v1.0.1.

### D. Namespace explorer

1. The exact URI `https://xmlsquish.moesegfault.dev/ns` is visible, selectable, and unchanged in both locales.
2. All eleven directives are present exactly once and grouped as specified; each has a stable fragment anchor.
3. With JavaScript enabled, filtering by name or contract updates visible cards and an announced result count; clearing restores all eleven.
4. With JavaScript disabled, the filter/copy enhancements are absent, the URI and example remain usable, and all eleven cards remain visible.
5. The page links to the current raw DSL, v0.3.0 and v0.2.0 snapshots, runnable examples, release migration information, license, and standards without implying that the namespace URI is versioned.

### E. Interaction, accessibility, and responsive quality

1. Product-page links have computed `text-decoration-line: none` at rest, hover, focus, visited, and active states.
2. Every link still has a recognizable affordance through geometry, weight, icon/badge, border, background highlight, and/or focus outline; color alone is not the only hover/focus signal.
3. Keyboard traversal exposes a visible 3 px focus indicator and follows visual reading order; skip navigation reaches `#main`.
4. At 320, 390, 768, and 1440 px in light and dark themes, `document.documentElement.scrollWidth <= innerWidth + 1`; only bounded code/technical components may scroll internally.
5. At 200% zoom, navigation, headings, cards, downloads, vocabulary, and footer remain readable and operable without two-dimensional page scrolling.
6. `prefers-reduced-motion: reduce` removes lift/translation animations without removing state feedback.

### F. Publication gate

1. Production build, Astro type check, unit/browser tests, and link/metadata contract tests pass.
2. Both locales and all three human destinations return HTTP 200 from the deployed domain.
3. GitHub `v1.0.1` is immutable and the public Release is non-draft/non-prerelease unless explicitly labeled otherwise.
4. Every advertised asset and `SHA256SUMS` returns HTTP 200, and independently observed digests agree with the published manifest.
5. Visual review confirms that Home remains recognizably unchanged while Release log and Namespace now belong to the same product family.

## 14. Product risks and mitigations

| Risk | Why it matters | Mitigation |
| --- | --- | --- |
| “Integration” becomes three pages with copied CSS | Visual drift returns on the next release. | Shared shell and primitives; page-specific composition only. |
| Removing underlines makes links invisible | Aesthetic compliance would reduce usability and accessibility. | Persistent weight/arrow/badge or card geometry, accent wash on interaction, 3 px focus, contrast checks. |
| Release page becomes another home page | Returning users cannot scan actual changes. | Enforce the distinct release hierarchy and remove duplicated product journey content. |
| Namespace redesign becomes a docs framework | Complexity overwhelms eleven directives and violates the product-interface request. | One searchable grouped catalog on one page; raw spec remains linked. |

| Mobile menu hides key routes | Current CSS already hides the main nav below 800 px. | Explicit mobile acceptance test with JavaScript disabled and keyboard access. |
| Namespace version is confused with executable version | Users may invent a `/ns/1.0.1` URI and break XML identity. | Repeat the three-way distinction: stable URI, specification snapshot, product release. |

## 15. Final recommendation

Implement this as a **single coherent product shell with three specialized surfaces**, not as a marketing site plus docs. Preserve Home almost exactly; make Release log chronological and action-oriented; make Namespace visual, grouped, and searchable. Use the current home page's coral highlight language everywhere instead of underlines. The smallest complete v1.0.1 experience is therefore three stable routes, one shared shell, one release source of truth, one namespace catalog, and behavior-focused tests that prove the site remains usable across locale, theme, viewport, keyboard, and no-JavaScript conditions.
