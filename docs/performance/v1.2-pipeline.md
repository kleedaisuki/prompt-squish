# v1.2 pipeline performance and CI policy

## Measurement contract

`scripts/perf/measure.py` measures the shipped release CLI as a new subprocess for
every observation. It includes startup, source discovery, front end, middle end,
linking, back end, project-cache access, publication and process exit. Streams are
captured, color and tracing are disabled. It does not measure terminal rendering,
Rust compilation, or network dependency acquisition.

| Workload | Probe | What it can distinguish |
| --- | --- | --- |
| `startup` | `--version`, 5 processes | Startup constant factors |
| `tiny.cold` | Tiny prompt, project build root removed before every observation | End-to-end uncached compilation |
| `tiny.warm` | Identical tiny prompt, existing project cache | Cache verification / publication constant factors |
| `prompt.distinct-macros-{1,64,2048}` | Distinct definitions, each expanded once in a prompt | Macro address-index scaling without ZIP bytes masking evaluation |
| `prompt.literal-regex-{1,64,2048}` | One literal-pattern macro repeatedly invoked | Regex specialization/pool reuse in uncached builds |
| `pack.assets-{1,64,512}` | 64 KiB asset repeated under unique names | ZIP construction, asset loading, output-size scaling |
| `pack.distinct-includes-{1,64,512}` | Distinct entry roots importing one shared module | Included-entry memoization, compact link-closure scaling |
| `sopack.macro-reuse-{1,64,512}` | Precompiled dependency, distinct asset macros, removed producer tree | Compiled-module reuse, definition-site relocation, linking scaling |

Cold means **empty project cache**, not cold OS page cache. The 512-asset fixture
contains 32 MiB of stored ZIP member data: this is an intentional long-tail
microbenchmark, not representative of ordinary tiny prompt builds. Each SOPack
fixture uses distinct macros because archive destinations are static and duplicate
member names are invalid. This measures reuse of an immutable compiled module,
not memoization of repeated identical macro results.

Each measurement retains nanosecond samples, median/min/max, binary SHA-256,
version, platform, Python version, CI commit and runner identity. Fixture creation,
cache removal and artifact hashing are outside the timed region. Every archive
is rebuilt from an empty project cache and compared byte-for-byte; ZIP member
ordering, uniqueness, fixed DOS epoch and path safety are checked separately.
SOPack production is outside consumer timing; the archive is moved to a new
directory and the producer tree deleted before consumer dependency resolution.
Binary asset bytes and archive immutability are checked after the build.
An additional untimed tiny cold build enables `--trace=events` and embeds the
persisted pipeline JSONL records in the report. This gives end-to-end phase
evidence while keeping default-off telemetry overhead out of latency samples.

```sh
python scripts/perf/measure.py target/release/xmlsquish \
  --scratch .temp/performance --report .temp/performance/results.json
```

An optional `--baseline PATH` compares startup, tiny prompts, distinct macro
definitions and literal-regex prompt workloads:
the old binary cannot meaningfully provide a baseline for a new archive feature.
Both binaries use separate fixture/cache roots. Candidate and baseline processes
alternate AB/BA per observation and report paired candidate/baseline ratios. The
long-tail prompt corpora are identical and use empty project caches for every
sample; final prompt bytes must be exactly equal before a ratio is accepted,
and both hashes are retained for provenance.
Distinct definitions and literal regex are supported by v1.1, unlike archives.
The
CI baseline is the fixed official v1.1.0 Linux release binary; its archive SHA-256
is verified against published `SHA256SUMS` before reading its sole executable.
For optimization decisions, repeat independent paired runs
on the same idle machine and compare artifact semantics separately. Shared hosted
CI machines provide descriptive trends, not a strict latency regression gate.
No measured speedup is claimed until actual results have been collected.

## CI resource and release safety contract

- Rust caches are partitioned by OS, architecture, pinned toolchain, job/profile,
  lockfile and commit, with lockfile-scoped restoration. Cache contents are only
  rebuildable Cargo registry/git/build state, never project trace data or secrets.
  Restore and save are explicit separate steps: non-cancelled failed checks still
  save partial dependency compilation under their exact-commit key, unless that
  immutable key already exists. Subsequent fixes restore the lockfile-scoped cache
  and Cargo rechecks source fingerprints; a failed run is never release evidence.
- `cargo test --all-targets` already builds its test targets. CI therefore removes
  the preceding redundant workspace build and explicitly builds only the composed
  CLI needed by smoke tests. Source installation uses the debug profile already
  populated by testing; shipped native binaries still use the release profile.
- The Linux performance job is opt-in via `workflow_dispatch` input `performance`
  (default false), avoiding repeated release builds during ordinary fix iterations.
  Final release verification explicitly enables it. It builds the actual release binary and uploads raw JSON
  evidence for 30 days, including partial failure information when probes fail.
- Dispatch input `site` defaults to true. Rust-only fix iterations may explicitly
  set it to false after site validation has passed for unchanged site content;
  push/PR runs always validate the site. Final release verification dispatches
  with both `performance=true` and `site=true` for complete exact-commit evidence.
- Cross-platform Rust jobs wait for the quality job's explicit compile outcome.
  A failed type check prevents expensive native tests; a successful type check
  followed by a formatting/lint failure still permits runtime feedback in that
  same CI run. The quality job and overall CI remain failed, so this never weakens
  release authorization. Optional performance measurement still requires the
  complete quality job to pass. Site validation remains independent.
- Release resolution requires a successful **exact-source-SHA** `ci.yml` run from
  `push` or `workflow_dispatch`. Another workflow, a PR merge commit, a successful
  older commit, or an in-progress run cannot authorize publication. Development
  branches can dispatch CI before tagging; merging is not required by this gate.
- All six release targets retain real native archive/CLI smoke tests. Linux and
  Windows x86 duplicate full regressions are removed because exact-SHA CI covers
  them. ARM targets and both macOS architectures retain full release regression
  suites. In particular macOS Intel is not silently dropped just because current
  `macos-latest` happens to select Apple Silicon.
- Only the final aggregation job has release write permission. The existing
  immutable tag resolution, complete matrix validation, checksums, legal notices,
  tagged SKILL asset and refusal to replace differing assets remain intact.
- Tests and generated measurements use repository `.temp`/`.cache`. macOS
  case-sensitive test volumes are created and mounted below `.temp` in CI.

Cache restoration is a performance hint, never correctness evidence. GitHub's
[dependency caching guidance](https://docs.github.com/en/actions/concepts/workflows-and-actions/dependency-caching)
and [artifacts guidance](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts)
explain the distinction. The peer-reviewed ICSE 2024 study
[Resource Usage and Optimization Opportunities in Workflows of GitHub Actions](https://software-lab.org/publications/icse2024_workflows.pdf)
motivates avoiding repeated work and measuring actual workflow costs rather than
assuming a cache always saves time. We do not treat its aggregate findings as a
project-specific speedup estimate.

## Verification status

Local validation intentionally consists of lightweight Python contract tests and
syntax checks, not expensive Rust builds. Real CLI archive and performance probes
must execute in GitHub Actions against the completed compiler/manager changes.
Record the resulting CI run ID and artifact before treating timing numbers as
release evidence. This document is the measurement protocol, not fabricated
benchmark results.

512 assets (33,608,726 bytes) took 243.726 ms; 512 distinct includes (96,168 bytes)
took 883.128 ms. Include time grew about 7.8 times from 64 to 512 entries,
consistent with roughly linear scaling over that interval. Output size alone
cannot explain its relative cost; phase evidence is needed before causal attribution.

**The run failed during SOPack fixture setup:** an absolute `add --path` violated

## Bounded profile experiment

The existing `ci.yml` includes a manual-only `profile` job, disabled unless
dispatch input `profile=true` (default false). It requires the quality job to
pass and does not bypass or disable normal native test jobs. It builds the same
source commit exactly twice: explicit release
settings `lto=false, codegen-units=16`, then `lto=thin, codegen-units=1`. Cargo
fingerprints effective profile flags. The default build uses `target` with a
fallback restore from the existing CI performance cache; ThinLTO uses the
separate `.cache/profile-target` directory. The combined experiment cache labels
both profile configurations. Copies of both executables
stay on the runner under `.temp/profile` and are never uploaded or downloaded.
`profile_probe.py` samples only startup, tiny cold and tiny warm builds, with
20 alternating AB/BA pairs, raw observations, executable sizes/hashes and exact
prompt-byte equality. Build wall times are recorded but may include unequal
cache warmth (especially the intentionally restored default build), so they
describe actual job costs, not a fair cold-versus-warm compiler-speed comparison.
No archive tails or v1.1 downloads occur in this experiment.
Only the small JSON reports are retained. The experiment itself does not edit
shipping Cargo settings; the evidence-based adoption decision is recorded below.

The performance job in [run 36774896484](https://github.com/kleedaisuki/prompt-squish/actions/runs/36774896484)
completed the entire harness at `e8b7ea3f9907563680bc68837974233fee9d1d60`.
This is a successful **performance job**, not a claim that every job in that CI
run passed. Full raw evidence, including all 64 untimed trace records, is retained
in [v1.2-hosted-complete.json](v1.2-hosted-complete.json).

| Paired prompt workload | v1.1 median (ms) | Candidate median (ms) | Median paired ratio |
| --- | ---: | ---: | ---: |
| Startup | 1.695 | 1.778 | 1.047 |
| Tiny cold | 21.951 | 23.664 | 1.085 |
| Tiny warm | 15.363 | 16.255 | 1.060 |
| Distinct macro definitions, 2048 | 235.674 | 232.216 | 0.987 |
| Literal regex expansions, 2048 | 209.794 | 123.959 | 0.591 |

The small-input concern reproduced: all five startup/cold/warm pairs exceeded
one again. The regex tail benefit also reproduced descriptively, while distinct
macro end-to-end benefit remained small. These two hosted runs still do not
establish statistical significance or explain the startup difference causally.
Exact long-tail prompt-byte equality passed. The default profile should not be
described as universally faster than v1.1.

| Candidate-only archive workload | 1 member (ms) | 64 members (ms) | 512 members (ms) |
| --- | ---: | ---: | ---: |
| Pack assets | 23.667 | 55.859 | 245.548 |
| Pack distinct includes | 27.834 | 113.330 | 720.040 |
| Relocated SOPack module/macros | 28.474 | 62.411 | 272.506 |

All archive workloads passed deterministic cold rebuilds. SOPack consumers
used workspace-contained archives after deleting the producer source tree, and
checked exact definition-site binary assets plus dependency archive immutability.
The shared include index introduced between runs is consistent with the 512-entry
time falling from 883.128 to 720.040 ms (about 18.5%), while the 64-entry observation
was essentially unchanged. This is a cross-run observation, not an alternating
old/new implementation comparison; scheduling/hardware differences prevent a
strong causal speedup claim.

The additional cold traced tiny invocation took 23.778 ms to command completion.
Action start/finish timestamps give compile 4.055 ms, link 1.717 ms, instantiate
2.214 ms, backend 1.631 ms and publish 5.434 ms; final catalog persistence took
3.160 ms and initial catalog recovery 2.072 ms. These are one **tracing-enabled**
invocation, not components to substitute into tracing-off benchmark medians.
Nonetheless publication and cache/catalog work are substantial relative to tiny
compilation, motivating a focused durability-preserving bookkeeping investigation.
There is no v1.1 stage trace, so this cannot identify the cause of the measured
regression. The separate same-source ThinLTO experiment provides the next startup
constant-factor probe; its results and adoption decision are recorded below.

## Same-source profile trial and adoption decision

The profile job in run `36774896484`, also at
`e8b7ea3f9907563680bc68837974233fee9d1d60`, completed with 20 alternating
pairs per workload. [v1.2-profile-trial.json](v1.2-profile-trial.json) retains
all samples, profile flags, binary sizes/hashes and actual CI build wall times.
This comparison changes build settings only, not source semantics or versions.

| Probe | Explicit default median | ThinLTO/cgu1 median | Median paired ratio | Pairs below 1 |
| --- | ---: | ---: | ---: | ---: |
| Startup | 1.708 ms | 1.616 ms | 0.940 | 17 / 20 |
| Tiny cold | 23.521 ms | 23.361 ms | 0.995 | 12 / 20 |
| Tiny warm | 15.688 ms | 15.281 ms | 0.968 | 13 / 20 |
| Executable size | 22,313,440 bytes | 18,680,496 bytes | 0.837 | Not a timed sample |

Exact final prompt bytes matched. Startup observations favor the smaller optimized
binary; tiny-cold evidence is essentially unchanged. Warm measurements are noisy,
with individual paired ratios from 0.687 to 1.636. These are descriptive results
from one hosted machine, not a significance test. Actual build wall times were
116.518 s for explicit default and 149.403 s for ThinLTO: an additional 32.885 s
of observed job cost, **not** a controlled compile-time regression estimate because
their restored dependency/profile cache warmth differed.

Decision: adopt release `lto="thin"` and `codegen-units=1` for the measured
approximately 16.3% binary reduction and startup constant-factor benefit, accepting
the observed bounded hosted build cost. The experiment does **not** resolve the
roughly 8.5% v1.1-relative tiny-cold overhead from the complete standard run.
The paired ThinLTO/default ratio must not be multiplied by a different runner's
v1.2/v1.1 ratio to manufacture a release speedup claim. Final normal CI must measure
the actual shipping profile against v1.1, including archive tails and default-on
site checks; the extra profile job is not repeated. A separate ordinary-prompt
cache-output simplification is being investigated to reduce unnecessary directive
metadata work without weakening archive semantics or durability.

## Shipping-candidate verification

[Run 36777315965](https://github.com/kleedaisuki/prompt-squish/actions/runs/36777315965)
passed the complete normal CI suite at
`1870f3b81024735c7e8482403bb217f87a51e904`, with site and standard performance
enabled, and the separate profile experiment disabled. The candidate combines
shipping ThinLTO/cgu1, ordinary-prompt two-output cache records and the shared
include index. [v1.2-shipping-hosted.json](v1.2-shipping-hosted.json) preserves
the actual v1.1 comparison, archive checks and 64 tracing records.

| Prompt workload | v1.1 median (ms) | Shipping candidate median (ms) | Median paired ratio |
| --- | ---: | ---: | ---: |
| Startup | 1.621 | 1.549 | 0.981 |

These are five actual alternating pairs, not earlier ratios multiplied together.
Final prompt bytes matched exactly for the long-tail comparisons. The previous
8.5% paired cold overhead is now a 2.0% observation; candidate changes and runner
conditions both differ, so this is not a controlled attribution of the reduction.
A small cold/warm cost remains, and the warm ratios range from 0.675 to 1.447.
We therefore retain the measured trade-off rather than claim universal improvement:
new archive/compiler capabilities have a small observed prompt-path overhead,
while startup and large-regex workloads favor the shipping candidate in this run.
The 2048-regex pairs all favor the candidate (ratios 0.535–0.566); independent
devices/runs would still be needed for general statistical claims.

Candidate-only 512-member cold medians were 228.884 ms for assets, 756.516 ms
for distinct includes, and 252.604 ms for relocated SOPack macros. Deterministic
ZIP rebuilds, exact binary assets and immutable dependency checks all passed.
The traced tiny invocation completed in 26.905 ms, with 7.072 ms in the publish
action; this tracing-enabled sample is phase context, not a substitute for the
tracing-off paired medians. No further speculative production change is justified
by this one report before release verification.
