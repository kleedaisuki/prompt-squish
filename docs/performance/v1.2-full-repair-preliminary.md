**Status: preliminary, not the final candidate or a release authorization.**

## Measurement contract

One hosted Linux runner: AMD EPYC 7763, four logical CPUs, Rust 1.88.0 / LLVM20.1.5, shipping ThinLTO and codegen-units1. Both versions compile their own four bench targets. Five samples per case, two warmups, adaptive 3ms target, capped256 operations; separate allocator binaries use one operation per allocation sample. Three AB/BA process passes (AB, BA, AB). These are independent process-group medians, not lockstep paired operations, confidence intervals, or significance claims.

Setup/output-drop boundaries are retained per row. Canonical document, complete trace and directive hashes agree for common core fixtures; ZIP transport/member hashes agree, and SOPack full normalized semantic oracles agree. The provider namespace change intentionally prevents requiring identical SOPack archive bytes. Duplicate-source-content topology strengthening is pending; this run does not establish that later oracle contract.

## Regressions and trade-offs requiring follow-up

- Large static scalar instantiation is slower despite fewer allocation requests: 16 selected64KiB regions ratio1.282, repeated64KiB fact ratio1.208, and single4KiB static fact ratio1.362. All three groups have the same direction; output oracles agree. This is an observed regression, not evidence that allocation reduction implies lower latency. Compiler owner notified; mechanism is not yet attributed.
- The owned compatibility `middle_clone_plus_call` on reused64KiB scalar is slower by4.747 ratio. It is not the manager prepared-facts path; it must remain visible rather than being conflated with production warm reuse.
- Borrowed ZIP writing at16MiB/32members has latency ratio1.038; the three-pass pattern should be checked before claiming any writer speed benefit. Borrowed reading removes the payload copies: cumulative allocated bytes33568166→4696, peak tracked extra-live33564142→3256. This peak is allocator-accounted memory above entry baseline, **not RSS**.
- Shared SOPack reading of512-provider cycle reduces cumulative allocated bytes13711988→6362672, but increases peak tracked extra-live3508139→3965467 (13.0%). Simultaneously retaining shared authoritative storage has a real peak-memory trade-off; lower cumulative allocation does not guarantee lower peak.
- Tiny owned middle compatibility adds one request and720 allocated bytes (1180→1900). This is not the warm prepared manager operation.

## Cold-tax and startup source-boundary audit

For D4096/E64/last-definition, candidate `prepare_unit_shared` takes
13.025/13.108/13.191ms across the three groups; `prepare_and_specialize_unit_shared`
adds little at this geometry (first group13.144ms), while specialization after
proof creation is about66us. This is a **substantial one-time cost**, not a free
prelude to the roughly2.5ms warm linked-facts measurement. Preparation requests698
allocations/72413 cumulative bytes with peak63807 and retained256; tiny preparation
is about8.1–8.4us,18 requests/548 cumulative bytes. The old link fixture already
has caller-provided snapshot revisions prepared outside timing, whereas the new
proof establishes actual content identity. Therefore these tax rows do not have
an API-equivalent old-stage baseline and cannot be called a measured13ms regression.
They are a necessary amortization boundary and must be checked in complete CLI
measurements, particularly first-use and many distinct units. Actual preparation
constructs `PreparedUnit::new` from raw shared IR; production can consume a sealed
verified decoder/encoder receipt without rehashing. These are different contracts;
receipt reuse must not disguise raw proof cost.

Source diff between the measured commits contains **no changes** to `src/main.rs`
or `crates/squish-cli/src/lib.rs`. The `--version` exit occurs in parser outcome
handling before environment capture, tracing, runtime, project discovery, or cache
opening. Thus the measured startup regression is not evidence of newly added
project/config or SOPack work on this route. Dynamic loader/binary layout or runner
variation are possible but unproven; the artifact records bench binary hashes,
not CLI executable sizes, so no size-based attribution is made. A source fix based
only on this small difference would be speculative. Preserve a repeated same-host
startup check on the final candidate instead.
