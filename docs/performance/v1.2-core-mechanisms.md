Production reference: main `2b9c8d00c5187ae83e2da8ee1b6746ad2df1f6cf` / immutable release v1.2.0.
Status: hosted baseline and same-runner origin-index comparison confirmed. Candidate

36813351009. The subsequent benchmark-only debug-smoke helper adjustment passed quality

## Why the earlier CLI comparison is insufficient

The preceding [source-overheads investigation](v1.2-source-overheads.md),
[first hosted raw report](v1.2-first-hosted.json), and
[complete hosted raw report](v1.2-hosted-complete.json) identified useful end-to-end behavior,
but process startup, CAS, durable publication and orchestration overlap compiler mechanisms.
A v1.1 comparison cannot establish whether v1.2 uses needlessly naive internal algorithms.
This experiment measures v1.2's actual public production APIs in one process, after inputs
have been frozen in memory. It has no process-per-operation, filesystem, CAS or backend.

## Real fixtures and correctness

Implementation: `crates/squish-link/benches/support/core_suite.rs`.
The only added domain dependency is existing internal `squish-xml-front` as a dev dependency;
no third-party benchmarking or allocator dependency is introduced.

Fixtures are generated DSL and compiled by the production frontend from SourceSnapshot memory
adapters. Their UnitRevision identities use real canonical container semantic/object digests.
Frozen closures and containers are fully validated and round-tripped before measurement.
Every entry is linked and instantiated through public StaticLinker/Instantiator APIs;
exact expected text, empty directives, document validity and complete trace/document validity
are asserted before any warm-up or sample. Origin attribution and invocation budgets remain
active in measured calls. Inputs are never read from a filesystem inside a sample.

Pairs that are output-equivalent can legitimately have different source/provenance identities:
first/last macro names and literal/dynamic scalar operations differ in source semantics.
Both complete traces are independently validated; this experiment does not pretend those
traces are byte-identical or disable source attribution to obtain a faster control.
The repeated/unique scalar pair fixes output and source spelling width, while legitimately
varying values recorded in frame argument evidence.

## Measurement boundaries and counter semantics

Two different benchmark executables share the same fixtures and sample support:

- **`core_latency`** installs no counting allocator. Latency uses the normal System allocator.
- **`core_allocations`** installs a benchmark-only System-forwarding counting allocator and
  emits allocation counts/bytes, not latency. Atomics and the tracking branch affect execution;
  those runs must never be interpreted as timing measurements.

Shared harness: `scripts/perf/mechanism_support.rs`. It checks alloc/grow/shrink/zeroed/free
accounting before observations. All unsafe code is restricted to this isolated benchmark
allocator forwarding contract. The baseline leaves production algorithms unchanged; the
follow-up changes only the private origin lookup described below.

Every core observation uses the prepared-input API. Setup occurs before the clock/counter
scope; the returned value is black-boxed and destroyed after measurement. Owned input
consumption/destruction inside the public API remains included. Rows state `setup_excluded`,
`drop_included:false`, and segmented timing. Calibration includes only operation durations;
per-operation clocks have a floor, measured by the borrowed-closure control. Very short
validation/control timings must be interpreted with that floor, not as exact nanosecond truths.

`middle_prepared_input` / `link_prepared_input` exclude cloning the owned input. Their
`*_clone_plus_call` counterparts include the real clone inside the same public API call.
`deep_clone_closure` and `deep_clone_linked_program` isolate ownership costs explicitly.
Where the selected unit has a proven scalar, `deep_clone_static_scalar` measures the exact
public fact Clone used by the shortcut against `borrowed_static_scalar_control` on the same
immutable fact; fact construction is outside both observations.
The difference is informative but not a perfectly additive decomposition: preparation changes
cache/allocator state. No fixture construction or correctness assertion runs in a sample.

Rows follow `xmlsquish.mechanism.v1` JSONL. Dimensions record actual units, operations, regions,
origins, semantic-string bytes, frozen source bytes, encoded-unit bytes, frames, document
items, trace origins, scalar values, folded scalar facts and compiled patterns. Latency rows
provide total `elapsed_ns` and `iterations`; divide before summaries. Allocation observations
provide successful calls, requested allocated bytes (including each successful realloc's new
size), deallocation/reallocation counts and peak/retained live deltas relative to prepared
input memory. Allocated bytes are cumulative requests, not RSS or maximum retained memory.

`origin_scan_comparison_floor` sums witnessed static OriginId positions + 1 from frame
call/definition sites and dynamic SourceSpan nodes. These identities come from actual completed
provenance. In the released baseline each required a real successful linear origin lookup;
scalar/regex substitutions can add lookups not represented once in this sum. After indexing,
retain the raw dimension name and values for paired geometry: it is the baseline-equivalent
counterfactual work proxy, **not actual candidate comparisons**. It was never an instrumented
claim of total comparisons.

## Hosted collection and bounded smoke checks

```sh
cargo bench -p squish-link --bench core_latency --features mechanism-benchmarks --locked
cargo bench -p squish-link --bench core_allocations --features mechanism-benchmarks --locked
```

Cargo bench uses the bench profile (normally inherited from release); record effective Rust
version/profile/LTO/codegen settings, target, commit and executable digest in the hosted
manifest. Keep raw rows and host provenance. Proposed first bounded pass:
`MECHANISM_SAMPLES=5 MECHANISM_TARGET_US=3000 MECHANISM_MAX_ITERATIONS=256`.
Default support uses seven samples, two warmups, adaptive 10 ms operation-only batches and
one instrumented operation per allocation sample. The full suite uses bounded dimensions;
large cases are created and discarded one fixture at a time.

Cargo `test --all-targets --all-features` invokes only two tiny smoke fixtures via `--test`,
with one iteration/sample, not the scaling suite. Smoke still exercises actual compiler,
validators, persistence and both static/dynamic scalar paths. `--smoke` provides the same
explicit narrow mode. No local Cargo/npm was invoked for this workstream.

## Results and decisions

### Hosted baseline: run 36812006015

Source `54fe53f6275b004266cf946fb8fe2a352f196fa7`, production unchanged from the v1.2.0 tag.
Linux Azure runner, AMD EPYC 9V45, four logical CPUs; Rust 1.88.0 / LLVM 20.1.5;
bench inherits release ThinLTO/codegen-units=1. Five samples, two warmups, adaptive 3 ms,
256 repetition cap. Latency binary contains no counting allocator; allocation observations
come from the separate instrumented binary. Borrowed tiny control median is 19.398 ns,
so sub-100 ns differences remain especially sensitive to the segmented clock floor.
[Compact durable raw samples and host/executable provenance](v1.2-core-baseline.json)
preserve the following values; the complete hosted artifact contains all workload rows.

**Priority 1: linear origin lookup is a confirmed naive execution mechanism.**

At E=64, every first/last case emits exactly 66 document items and 65 frames. Within each
D pair, source byte length and all geometry except the counterfactual origin position floor
match. Both variants allocate exactly **781 calls / 273,061 requested bytes**; trace-only
validation stays approximately 0.39 microseconds across D. Thus output/provenance volume
or allocator growth cannot explain the substantial position-dependent execution cost.

| Definitions D | First macro instantiate median (us) | Last macro median (us) | First / last raw five-sample ranges (us) |
| ---: | ---: | ---: | --- |
| 1 | 23.919 | 24.035 | 23.732–24.135 / 23.889–24.164 |
| 128 | 27.054 | 36.042 | 26.998–27.109 / 35.643–36.422 |
| 1024 | 46.234 | 110.353 | 45.758–46.605 / 109.789–110.519 |
| 4096 | 98.054 | 344.042 | 97.484–100.937 / 342.505–345.766 |

The D4096 last case is 3.51 times its output-equivalent first case and 14.38 times the
D1 first case, with nonoverlapping sample ranges. Its legacy lookup floor is 788,709 versus
264,549 first; those values come from retained provenance positions, not timer instrumentation.
At D=1, E=256/1024 takes 99.688/513.063 us, with lookup floors 34,437/530,949. This also
exposes growing entry call-site scans, although the E sweep includes necessary frame/output
allocation growth and is not as discriminating as the fixed-E first/last comparison.

A single flat per-unit first-origin index is the authorized first intervention. It keeps
original table positions and object qualification, ignores out-of-range Region/Definition
metadata without tightening validation or growing by metadata IDs, and retains Region-first
then first-operation fallback. One allocation is sized by operations+regions+definitions;
lookup becomes constant time. The index is session-only, rebuilt on cache reconstruction,
and cloned with the executable. Setup/link/clone and tiny allocation overhead therefore
remain part of the same-runner comparison below, not costs to conceal.
Focused tests cover differential linear first-match behavior, duplicate/gapped metadata,
fresh/cached full-result identity, root priority/fallback, missing-root/definition errors,
invalid-operation rejection and distinct unit object qualification. No local Cargo was run.

**Priority 2: scalar interning is a measured follow-up candidate, not yet isolated.**

At K=2048, fixed eight-byte arguments and constant ignored-argument output, unique values
cost 4.822 ms [4.788–4.863] versus repeated values 1.652 ms [1.648–1.662]. Their origin
position floor is identical (2,112,517). Requested bytes increase only 2.09%:
11,212,357 versus 10,983,213; allocation counts 45,191 versus 41,087. At K512/width256,
unique values take 869.792 us versus 294.257 us repeated. Linear string interning plausibly
explains much of this cost, but necessary scalar table population/canonicalization also
changes; origin scans are quadratic in both controls. First remove the independently
confirmed origin scan, then rerun this sweep before replacing interning or assigning a
precise share of time to it.

**Other useful positive and negative findings:**

- At 4 MiB uncalled literal payload and fixed E16 output, prepared link is 6.989 us,
  clone-plus-link 79.536 us, closure clone 73.839 us. Instantiation stays 7.281 us,
  essentially unchanged from 64 KiB payload (7.283 us), with exactly 235 allocation calls /
  66,469 requested bytes in both. Large immutable payloads mainly reveal ownership copying,
  not execution of unused text. Do not claim a size-dependent evaluator regression here.
- A reused 4 KiB static scalar clone performs two allocations / 4,120 bytes per use.
  Nevertheless static K256 instantiation is 1.186 ms versus dynamic 1.927 ms, despite
  larger requested allocation bytes (8,655,865 versus 7,659,257), with equal 12,418 calls.
  At 64 KiB/K16, static 0.883 ms also beats dynamic 1.586 ms. Redundant copies are real,
  but the current shortcut is **not a measured latency regression**. Any borrowing change
  must preserve its useful compile-time behavior and exact provenance.
- An unused 256-pattern pool costs 1.873 ms middle-end time and 40,584 calls / 5,404,982
  requested bytes although only the main macro executes. Instantiation is 1.281 us versus
  1.177 us with an empty pool. Eager compilation is concrete startup work, but rejecting or
  lazily validating unused malformed patterns would alter language contracts. A future
  split must retain full validation and prove a worthwhile session-cache strategy.

### Same-runner index comparison: run 36813351009

Pinned baseline `54fe53f6275b004266cf946fb8fe2a352f196fa7` and indexed candidate
`fafbdaa3368f3843a18c2a1aa2be58b48f14c046` use the identical current harness with
`MECHANISM_ORIGIN_ONLY=1`; there is no benchmark algorithm substitute. This runner is an
AMD EPYC 7763, **not** the first baseline's EPYC 9V45: compare the adjacent baseline/candidate
pairs here, not absolute times across the two CI runs. Rust/profile/sampling remain 1.88.0,
ThinLTO/codegen-units=1, five samples, two warmups, adaptive 3 ms and cap 256.
Three pairs execute in order **AB, BA, AB**, six process executions in total. Each process
measures actual API operations in-process; process startup never enters an operation sample.
The ratio is the median of three adjacent process-pass median ratios, not a pooled-sample
ratio or a statistical confidence interval. Times below are medians of the three pass medians.

[Compact selected report](v1.2-origin-index-comparison.json) preserves 19 latency cases,
their 15 raw observations per variant, all paired pass medians, host/profile/executable/harness
digests, 12 allocation case pairs with all five observations, and ten exact output oracles.
**All ten fixtures have identical canonical document, complete trace and directive fingerprints
and geometry in all six executions.** Each process also performs the ordinary semantic and
complete-provenance validators outside samples. This establishes unchanged successful output
for these fixtures, not equivalence for every malformed input or every possible DSL program.

**The index removes the measured definition-position pathology.**

| Definitions D, E=64 | Baseline first / last (us) | Indexed first / last (us) | Paired indexed/baseline first / last |
| ---: | ---: | ---: | ---: |
| 1 | 45.104 / 45.230 | 42.168 / 42.672 | 0.936 / 0.943 |
| 128 | 51.682 / 62.905 | 44.261 / 44.827 | 0.856 / 0.714 |
| 1024 | 83.482 / 169.454 | 44.140 / 44.233 | 0.531 / 0.261 |
| 4096 | 180.117 / 530.404 | 44.726 / 44.314 | **0.250655 / 0.083548** |

At D4096, first-case latency is 74.93% lower and last-case latency 91.65% lower. The three
paired ratios occupy 0.247630–0.252068 first and 0.083081–0.084900 last. Across all 15 raw
observations, first changes from 176.914–181.509 us to 44.501–45.587 us; last from
520.413–550.953 us to 43.319–44.728 us. These large, nonoverlapping ranges and the disappearance
of the first/last gap support a causal mechanism improvement, not merely a favorable single
sample. Output remains 66 items / 65 frames and runtime allocations remain exactly
781 calls / 273,061 requested bytes in every first/last case.

At D1/E1024, complete instantiation changes from 1,043.724 us to 664.322 us, paired ratio
0.636492 (three-pair range 0.632460–0.671267), or 36.35% lower. This also removes repeated
entry call-site scans, while necessary frame/output construction still grows with E.
The private implementation builds the index at `program.rs:83-86,161-220`, then performs
object-qualified lookup at `program.rs:140-153`; `instantiate.rs:1072-1096` retains Region-first,
then the region's first-operation fallback. It costs O(origins + operations + regions +
definitions) to initialize and O(1) per valid arena lookup, replacing repeated linear searches.
The portable IR/source tables are never renumbered or rewritten.

The paired increment is the median of pairwise differences; it need not equal the difference
of separately displayed medians. The borrowed control is about 27.14 ns here. Tiny link's
approximately 83 ns overhead is visible but should not be represented as precise universal
startup cost. Tiny instantiation's ratio is 0.984593, with overlapping raw ranges; this is
not grounds for a meaningful tiny-workload speedup claim. The index moves work into link
and retained executable data rather than making every phase uniformly cheaper.

Separate instrumented observations confirm prepared link and executable clone each add
**two successful allocation calls / 72 requested bytes** for tiny and **three calls /
98,920 bytes** for D4096/E64. D4096 clone retained/peak logical-live delta increases by
98,920 bytes; prepared link peak increases from 2,825,742 to 2,924,662 bytes and net retained
delta from 1,941,573 to 2,040,493 bytes. Tiny prepared-link peak rises only 26 bytes because
its largest transient occurs at a different point; this does not erase the 72-byte cumulative
request increase. These are accounting deltas relative to prepared input, **not RSS**.
Instantiation allocation counts, requested bytes, peak and retained deltas are identical
between baseline and indexed candidate, including tiny (34 calls / 5,671 bytes) and D4096.
The allocation runs are independent instrumented full-suite executions on different CPU
models; they support exact counting comparisons, not a cross-machine latency claim.

This is a deliberate trade: bounded session construction/storage overhead buys much lower
repeated provenance lookup cost. A one-shot tiny entry cannot amortize it, but the measured
long-tail execution benefit comfortably exceeds the observed setup tax on these fixtures.
Do not add independently timed phase medians into an asserted end-to-end throughput number.
Build wall times also have unequal cache warmth and are not a compile-time speed experiment.
No v1.1 comparison or CLI throughput claim substitutes for this controlled result.

### Remaining core priority after indexing

The indexed full-suite run repeats the ignored-argument scalar control on its own runner:
K2048/width8 repeated values take 1.773 ms [1.771–1.783], unique values 11.091 ms
[10.546–11.361], with equal source byte length, output (2,050 items) and frame count (2,049).
Requested bytes remain 10,983,213 versus 11,212,357 (+2.09%). These are **within-candidate**
observations, not a before/after comparison with the first baseline's CPU. After removing
the independently established origin scans, scalar interning remains the strongest next
core investigation. Multiple unique values necessarily change scalar table population and
canonicalization, so the entire 6.25-times difference is not yet attributable to interning.
A narrow first-insertion index preserving arena IDs, followed by the same exact output/trace
oracle and setup/allocation accounting, is the discriminating next intervention; it is not
part of this origin-index patch.


External grounding: [Rust black_box contract](https://doc.rust-lang.org/std/hint/fn.black_box.html)
is best-effort optimization resistance, not a formal timing guarantee;
[GlobalAlloc](https://doc.rust-lang.org/std/alloc/trait.GlobalAlloc.html) defines forwarding and
failure contracts; [Cargo bench targets](https://doc.rust-lang.org/cargo/reference/cargo-targets.html#benchmarks)
allow explicit harness-free measurement executables. Relevant older performance documents
remain background evidence, not the causal verdict for these in-process experiments.
