# v1.2 middle-end allocation and validation repair

Date: 2026-10-01. Scope: `crates/squish-link/src/middle.rs`.

The reviewed scalar selection allocated one temporary vector per macro call, inserted
region IDs into a tree set, and cloned selected `Region` records (including their operation
vectors) before materialization. The repair walks borrowed call arguments, lazily allocates
one dense region flag vector, and passes borrowed regions in canonical arena order to
`literal_scalars`. No RenderText arguments means no flag allocation or scalar-region scan.

Duplicate and unordered references only set flags; they cannot reorder materialization or
charge the aggregate 8 MiB scalar budget twice. The existing 1 MiB per-scalar bound, exact
scalar values, operation-level provenance segments, and behavior of empty regions after
budget exhaustion are preserved. The persistent IR and source identities are unchanged.

Public `MiddleEnd::optimize` and additive `optimize_shared` retain full validation. The
crate-private `MiddleEnd::optimize_shared_validated` factors the same optimization body for
trusted linker boundaries that have already validated the exact unchanged shared unit.
Its caller contract does not permit trusting arbitrary externally decoded IR or skipping
first validation. `OptimizedUnit.unit` retains an `Arc<RelocatableUnitIr>` rather than an
owned copy. Owned entry points transfer their input into one Arc; shared entry points keep
the exact original allocation. Public cache reconstruction still performs initial validation.
A production-unused owned trusted wrapper was removed instead of suppressing dead-code checks.

Prepared-unit construction consumes a sealed raw-unit validation/identity proof; it does not
run regex engines or materialize middle-end facts. The first reachable link or cache hydration
specializes the **whole referenced unit**, compiling every pattern in that unit, including
patterns in uncalled macros, before binding/execution. Successful facts and source-qualified
errors are retained by a session-local `OnceLock`, so independent entries share the same
optimized allocation and compiled pool. A wholly unreferenced archived unit acquires no new
engine validation merely because its library is loaded: archive-wide structural/source/import
validation and manager reachability pruning remain separate. Local frontend strict checks are
unchanged. This preserves the previous reachable-unit middle-end boundary, rather than hiding
malformed unused patterns inside a referenced unit through per-pattern lazy execution.

A test-only thread-local attempt counter increments immediately before each pool `Regex::new`
invocation. Independent-entry regressions require zero engine attempts at raw preparation and
one complete shared-pool compilation across repeated links/hydrations; repeated initialization
failures must reuse the same error without recompilation. Counter deltas distinguish actual
compilation reuse from merely copying statistics. The counter is absent from production builds
and does not require global resets or interfere with parallel test threads.

Inline regressions compare duplicate/unordered selection against canonical materialization,
including aggregate cap exhaustion and empty-region facts; check no-selection allocation;
and ensure malformed public IR is rejected before regex pool indexing. Existing Unicode,
capture, provenance and size-bound tests remain intact.

Verification here: rustfmt only, by assignment. No local Cargo or npm runs, no commits,
and no measured performance improvement claimed. Hosted tests and discriminating benchmarks
remain the integration owner's responsibility. These are mechanism reductions, not timing
results; relate measurements to the broader `v1.2-core-mechanisms.md` baseline.

## Owned 64 KiB regression investigation (2026-10-01)

Evidence: `.temp/full-repair-0b1c732/pass-*-core_{latency,allocations}.jsonl`,
baseline `1bbf6cd`, candidate `0b1c732`, workload
`reused-scalar-e16-bytes65536-static1`. No Cargo or production edits were performed
during this investigation.

The fixture selects the macro **module**, not the entry: `core_suite.rs:114-123`
selects `sample_unit`, and only names starting with `scalar` override it at
`159-163`; `reused-scalar` does not meet that condition. Its single 64 KiB
literal scalar region is referenced repeatedly. Fixture construction and sample
selection are unchanged between these commits, as are the reported dimensions.

| Pass 0 median operation | Baseline ns | Candidate ns |
| --- | ---: | ---: |
| `validate_unit` | 408.9 | 430.4 |
| `middle_prepared_input` (owned input) | 2276.1 | 22495.0 |
| `middle_clone_plus_call` | 5521.2 | 25650.7 |
| `middle_shared_prepared_input` | unavailable | 2014.8 |

Passes 1 and 2 reproduce the same owned/shared separation (owned prepared
22961.8 / 23781.2 ns versus shared 2059.0 / 2024.8 ns). Candidate owned
preparation performs 13 allocations / 67270 bytes; shared preparation performs
12 / 66550. The difference is precisely one 720-byte Arc allocation, not
an extra literal-content clone. Public owned `optimize` constructs this Arc
before delegating to the exact same shared validation and fact algorithm.

IR validation cannot explain this separation: the entire `validate.rs` diff
only exposes `validate_source_key` as crate-private; `model.rs` is unchanged.
Codec, wire, persistence and digest improvements are not called by these
measured middle-end operations. No patterns exist in the selected unit, so
regex compilation is also excluded. The latency harness times only the
operation and drops its returned output after stopping the clock
(`mechanism_support.rs:156-171`); destruction still affects the next iteration's
allocator state.

The 4 KiB static counterpart has owned/shared prepared timings of 812.1 / 668.0
ns, and the dynamic 64 KiB counterpart (no literal pool bytes) has 618.8 / 535.6
ns. Therefore the evidence isolates an interaction between **early owned Arc
allocation and large literal materialization / allocator lifecycle**, rather
than a general scalar-discovery or structural-validation regression. The exact
glibc allocation-bin or page/cache mechanism is not proven by aggregate counters.

A discriminating next repair is borrowed fact analysis while the owned unit is
still stack-owned, followed by its single Arc allocation after materialization;
the shared path continues analyzing its existing Arc payload. Compare the exact
owned and shared controls above on the hosted runner. This changes allocation
order without dropping validation, provenance, size caps or shared ownership.

Implemented the allocation-order experiment in `middle.rs`: private `MiddleFacts`
analyzes validated borrowed IR; owned public optimization validates and materializes
these facts before its single `Arc::new` publication. Shared public/trusted paths
use the same borrowed analysis and retain their exact existing Arc payload. No IR,
text or fact copies were introduced. Regression coverage compares owned/shared
raw IR, facts, regex patterns and statistics on a valid module with a 64 KiB
scalar plus a literal regex decision; invalid public inputs retain identical errors.
Local verification remains rustfmt and diff checks only. **The measured regression
is not considered resolved until hosted measurements confirm the owned controls.**


### Second checkpoint: allocation-order hypothesis not confirmed

At `2cb7421` ([run 36830228524](https://github.com/kleedaisuki/prompt-squish/actions/runs/36830228524)),
reused-64 KiB owned clone timings were bimodal: baseline 25.549/5.393/27.410 us versus
candidate 26.187/29.981/5.211 us over the three process passes. Candidate shared middle
remained approximately 1.99–2.05 us. The order-only change did not demonstrate a causal fix;
aggregate medians that switch which process occupies the slow state must not be sold as a
stable allocator optimization. Sixteen-region owned clone ratios were 1.439/1.351/0.936.

The next actual execution representation shares repeated literal content privately, while
preserving public String facts: see [v1.2-core-remediation.md](v1.2-core-remediation.md#private-shared-scalar-facts-execution-versus-public-compatibility).
It removes proven sixteen-fold materialization in the linked program, not a guessed glibc
mechanism. Public owned controls remain separate, and the forthcoming run must expose their
mixed-direction/bimodal timing rather than hiding them under warm prepared-fact gains.
