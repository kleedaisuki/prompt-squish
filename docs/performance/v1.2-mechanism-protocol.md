# v1.2 in-process mechanism experiment protocol

## Question and scope

Released v1.2 versus v1.1 CLI comparisons establish user-visible aggregate cost,
but cannot reveal whether v1.2's internal representations are unnecessarily naive.
These probes isolate actual production APIs and compare explicitly labeled simple
controls on the **same v1.2 implementation**, with independent input dimensions.
The released `v1.2.0` tag remains immutable. This document began as a
benchmark-only baseline protocol, before production changes were justified by
discriminating measurements and correctness evidence. That original scope is
historical: the current v1.2.1 repair candidate changes real compiler, archive,
manager and storage mechanisms. The measurement separation defined here still
applies, but its early smoke results are not current full-repair performance
or final release authorization. See the [current repair release draft](../releases/1.2.1.md)
and [preliminary same-host full comparison](v1.2-full-repair-preliminary.md),
which retain regressions and identify later fixes that require a final rerun.

This protocol follows the separation of setup, repetitions, optimizer barriers,
memory counters and complexity dimensions described by the production-proven
[Google Benchmark user guide](https://google.github.io/benchmark/user_guide.html).
We implement the small required subset using Rust's standard library rather than
adding a benchmark framework/dependency to the workspace. The ASPLOS 2009 paper
[Producing Wrong Data Without Doing Anything Obviously Wrong!](https://www2.ccs.neu.edu/racket/Performance/mytkowicz.pdf)
shows how apparently innocuous execution-layout factors bias measurements; this
motivates recording machine/toolchain/profile context and treating one hosted
process's results as observations, not universal causal conclusions.

## Four deliberately separate binaries

| Package | Target | Allocator | Evidence |
| --- | --- | --- | --- |
| `squish-link` | `core_latency` | Unmodified default System allocator | Core production API timings |
| `squish-link` | `core_allocations` | Bench-only counting System wrapper | Allocation calls/traffic/live deltas, never speed |
| `squish-backend` | `archive_latency` | Unmodified default System allocator | Real reproducible ZIP/SOPack encode/decode timings |
| `squish-backend` | `archive_allocations` | Bench-only counting System wrapper | Archive allocation behavior, never speed |

All targets use `harness=false` and opt-in `mechanism-benchmarks` features. The
common support file is `scripts/perf/mechanism_support.rs`, imported as a module
by each target; it is never linked as instrumentation into the production CLI.
Debug-profile execution selects tiny correctness-smoke fixtures and one sample,
as does an explicit `--test` argument. Cargo's all-target testing does **not**
reliably pass `--test` to harness-free executables; this was observed in hosted
Linux logs, where the earlier argument-only rule accidentally ran the full suite.
The corrected helper keys ordinary native smoke behavior to debug assertions.
Shipping-profile bench builds disable debug assertions and still collect the full
selected microbenchmark suite. The hosted collector builds only these four executables,
not every workspace test executable, and uploads only small JSON/JSONL evidence.

### Historical baseline smoke check (not current repair evidence)

The corrected debug path was checked against actual Linux logs in
[run 36815058201](https://github.com/kleedaisuki/prompt-squish/actions/runs/36815058201)
at `2d93ce8`: 41 native test-result groups total **705 passed / 0 failed**;
all four benchmark executables together emit **84 smoke observation rows**, each
with sample index 0 and exactly one iteration. Core workloads are only
`macro-d1-e1-last0-payload0` and `scalar-e2-static1-bytes8`; archive workloads are
bounded ZIP/SOPack/fanout smoke cases. Rust quality and all three native jobs also
passed. This is observed execution evidence, not an assumption about Cargo
arguments. Earlier full debug samples are not shipping-profile performance evidence.

Core ownership includes real validation, middle-end specialization, static linking,
instantiation, codecs and provenance. Archive ownership includes public reproducible
ZIP and SOPack readers/writers, source relocation and explicitly labeled payload
clone controls. Benchmark owners document each fixture and its semantic checks.
Independent dimensions are preferable to increasing every size together: definition
count versus expansion count, source/provenance table size versus emitted events,
archive member count versus total bytes, unit count versus asset bytes. A deep
clone or borrowed-view control exposes representation cost but is not automatically
an API-compatible proposed replacement.

## Sampling and ownership boundaries

Environment defaults: seven samples, two untimed warmups, 10 ms latency target,
adaptive power-of-two batches capped at 1,024 operations, and one operation per
allocation sample. These limits are explicit in the hosted environment and can be
overridden within bounded positive ranges. Both fixture setup and semantic assertions
occur outside measurement. `std::hint::black_box` consumes operation results.
The first hosted pass explicitly uses five samples, a 3 ms target and a 256-operation
cap because the core suite contains many independent mechanism/dimension cases.
Its exact overrides are recorded in provenance; these are not silently reported
as the library's seven-sample/10 ms defaults.

| Support API | Setup boundary | Returned-result destruction | Clock method |
| --- | --- | --- | --- |
| `latency` / `allocations` | Existing fixture outside closure; deliberately measured ownership work stays in closure | Included | One interval per latency batch |
| `latency_prepared` | `prepare()` before each interval | Excluded | Per-operation intervals summed per batch |
| `allocations_prepared` | `prepare()` before baseline gauge | Excluded | No reported time; exactly one operation/sample |

Prepared latency avoids retaining thousands of large cloned inputs simultaneously,
but incurs an `Instant` clock-read floor for every operation. A similarly segmented
no-op control is needed to interpret very small operations; it is not subtracted
silently from measured samples. Consumed **input** destruction inherent in the owned
production API remains part of the call, even when returned-output destruction is
excluded. Reports explicitly record `drop_included`, `setup_excluded` where relevant,
and `timing="segmented_operation"` for prepared latency. Do not merge measurements
with different lifetime boundaries.

Latency adaptation/warmup is discarded, not used as a result. Raw elapsed nanoseconds
and actual iterations are retained. The parser computes latency and allocation
traffic per operation; it does **not** divide a live-memory peak by batch iterations.
Output serialization and printing happen after the interval/counting scope closes.

## Allocation semantics and safety

`TrackingAllocator` wraps `System` only in allocation executables. Unsafe pointer
operations forward the same pointer/Layout and preserve allocation failure behavior;
the wrapper never reads payload memory, recursively allocates, formats text or takes
locks. Its implementation documents every unsafe block and the GlobalAlloc contract.
Successful allocations and zeroed allocations count once; successful reallocations
count as allocation requests for the complete requested new size, with a separate
reallocation counter. A failed reallocation retains the original live allocation
and contributes no successful request. Deallocation count covers explicit dealloc
calls, not the internal freeing done by a successful System realloc.

Process-global atomics account all successful live allocation lifetimes even when
sampling is off. The sample records its entry live gauge **without resetting it**,
resets only sample traffic counters, and seeds peak to the entry baseline. Grow and
shrink reallocations update the live gauge by their size delta. Reported extra peak
is `max(0, peak_live - entry_live)`; retained extra live bytes use the same baseline.
Destroying pre-existing inputs can lower live memory below that baseline, so a zero
extra peak does not mean the operation made no allocations. Requested allocation
traffic, extra live peak and retained live bytes are distinct metrics.

These are allocator-requested bytes, **not RSS, OS allocation size, allocator arena
reservation, stack size or a promise of lower total memory**. All benchmark-owned
workers must be quiescent at scope boundaries; workers started within an operation
must be joined before it returns. Atomics safely aggregate concurrent calls within
the process, but do not attribute them to individual threads. Exclusive scope
ownership prevents two sampling intervals from resetting each other's counters.
An unwind-safe guard disables tracking. Counters are snapshotted before releasing
scope ownership. Background allocations outside the benchmark's ownership would
contaminate counts and are prohibited, not magically filtered out.

`verify_allocation_accounting()` performs a small untimed alloc/grow/zeroed/shrink/
dealloc fixture and checks request count, requested bytes, deallocation count,
reallocation count, extra peak and restored baseline. Owners run it before results
in both binary modes. It does not issue dangerous giant allocations to force an
OS failure. Null-result branches preserve the underlying allocator contract.

## Hosted execution and evidence

The existing CI workflow has optional dispatch input `mechanisms` (default false).
One Linux job runs only after the full quality job succeeds. Normal native/site
gates and exact-SHA release authorization are unchanged: an experiment does not
provide a way to bypass tests. Standard CLI performance and the two-build ThinLTO
trial need not run again to collect these in-process measurements.

```sh
# Root agent dispatches remotely; no local Cargo build is required.
gh workflow run ci.yml --ref codex/v1.2-mechanism-benchmarks \
  -f mechanisms=true -f performance=false -f profile=false -f site=false

# After downloading JSONL only, validate/summarize without compiling Rust:
python scripts/perf/mechanisms.py --directory .temp/mechanism-summary \
  --summarize .temp/mechanisms/core_latency.jsonl .temp/mechanisms/core_allocations.jsonl
```

`mechanisms.py` records source SHA, immutable released-v1.2 tag SHA, package version,
CPU model(s), logical processor count, OS/Python, `rustc -vV`, shipping profile,
profile overrides, sampling overrides and GitHub run ID. Executable hashes/sizes
are recorded without uploading executables. Cargo's actual artifact paths are read
from its JSON stream, not guessed from hashes. Raw sample JSONL and the validated
summary report persist below project `.temp` and as short-lived CI artifacts;
durable findings and selected evidence will be checked into `docs/performance`.
Cache keys and restoring existing main-performance build state reduce first-run
waiting time. Failed experiment builds save partial compilation, never count as
successful performance evidence, and do not alter the released version.
The broad same-toolchain performance-cache fallback also covers a changed lockfile
caused by the internal frontend dev-dependency; Cargo still verifies dependency and
source fingerprints. Compiler stderr is retained with reports for failed-build
diagnosis, but no executable or target-directory artifact is uploaded.

## Interpretation rules and next decisions

- No latency estimate comes from the instrumented allocation executable.
- No CLI startup/I/O claim comes from an in-process microbenchmark.
- No naive control becomes a proposed replacement without the same correctness,
  ownership, provenance, relocation, validation and resource-limit contracts.
- Preserve raw samples and negative findings; report scaling and allocator traffic
  alongside medians. A hot path with O(definitions × events) source evidence should
  be probed by changing those dimensions independently before rewriting it.
- Use fresh processes/changed case order or independent hosted runs when a close
  result may depend on warmed state or code layout. The first pass locates costs;
  it does not provide confidence intervals or causal certainty.
- Freeze production implementation until probes identify a consequential cost;
  then make the smallest semantics-preserving change, remeasure actual mechanisms,
  and separately verify end-to-end behavior and durability.

Status: protocol and harness added; no mechanism performance results are fabricated.

## Same-runner origin-index intervention

Optional `origin_compare=true` extends the existing mechanism job, never the normal
release gates. It can run after a full candidate suite (`mechanisms=true`) or alone
as a narrowly targeted comparison (`mechanisms=false`). The pinned pre-index source
is `54fe53f6275b004266cf946fb8fe2a352f196fa7`; the candidate is the actual checked-out
commit. A detached reference worktree lives at `.temp/mechanism-origin-reference`.
Only current **benchmark** source (core suite, latency wrapper and shared harness)
is overlaid into that tree, with hashes recorded. No candidate production file is
copied into the baseline. Identical release/bench manifest profiles are checked.

Only `core_latency` is built for each source. The baseline uses isolated
`.cache/origin-reference-target`; the candidate reuses its own `target` after the
optional full suite. Cargo targets are never shared between different production
sources. Baseline compilation has its own cache. Build wall times describe hosted
job costs, not a fair old/new compiler-throughput comparison.

`MECHANISM_ORIGIN_ONLY=1` selects tiny, independent definition-first/last probes
at fixed expansion count, and a larger expansion-count control. The core owner
retains linking/index preparation, owned cloning and instantiation mechanisms,
so a lookup improvement cannot hide its setup or representation cost. Fixtures
run the same untimed semantic/document/provenance assertions in every process.
The core suite also emits one `xmlsquish.mechanism.oracle.v1` metadata record per
fixture, outside all samples, hashing the actual canonical document, full expansion
trace and archive directives separately. The collector does not aggregate these
records as timings. Every baseline/candidate process must provide the exact same
fixture map and three SHA-256 fingerprints or the comparison fails before any
ratio is accepted. Identical assertion source alone is therefore not mistaken for
independent cross-version output equivalence.
The analytical naive linear-scan comparison floor describes fixture geometry;
it is not a counter claiming that an indexed implementation still scans linearly.

Three process passes run AB, BA, AB on **one hosted runner**, retaining each phase's
position/version/raw JSONL. For each identical workload/mechanism/dimension and
lifetime boundary, the comparison pairs that pass's process medians and reports
all ratios plus their median/min/max. These are not lockstep paired operation
samples, and changing case order between versions is not falsely described as
independent operation pairing. A dimension mismatch or failed oracle aborts the
comparison. Large mechanism scaling differences can support the proposed causal
intervention; close tiny differences still require caution about code layout,
clock floors and process/allocator state. No cross-run ratio substitutes for
this same-runner experiment.

## Preparation-only legacy archive and CI waiting policy

Manual dispatch `legacy_fixture_only=true` is explicitly **not verification**.
It skips current-source quality/native/site jobs and runs one short Linux job
without installing Rust. `legacy_fixture.py` obtains the official shipped v1.2
Linux archive over HTTPS, checks its unique published SHA-256 entry, reads only
the named regular executable, and confirms `--version`. That writer builds a
foreign-provider package: public root macro `m:bundle` imports `pkg:provider/main`
and expands provider macro `p:asset`, retaining exact binary bytes in `legacy.bin`.
The output must include old `_providers/` paths and reproduce byte-identically
after `clean`. Only `tests/fixtures/v1.2.0-library.sopack` and small writer/fixture
provenance are uploaded. No old executable is downloaded to the developer machine.
The frozen archive is committed before running the mandatory new-reader regression.

The release gate now examines actual latest-attempt job conclusions, not just a
successful workflow header: quality, all three native platforms and Site must
each complete successfully at the immutable source SHA. A successful preparation
workflow or skipped-site fix iteration cannot authorize release. Native test jobs
again require full quality success, avoiding three costly platform builds after
failed Clippy. Explicit preparation controls default false; normal push, PR and
final full-verification platform coverage remains intact.
The latest-attempt selection follows GitHub's
[workflow-job REST API](https://docs.github.com/en/rest/actions/workflow-jobs),
which distinguishes current jobs from earlier executions of a rerun.

## Full-repair same-runner comparison

The pinned pre-full-repair source is `1bbf6cd0ec9827a186da18fa0cbe8943257fa8fc`.
`full_repair_compare.py` compiles **version-specific** core/archive latency and
allocation executables at that source and at the candidate, using separate Cargo
targets and identical shipping-profile settings. It does not overlay a candidate
harness that calls newly added shared APIs onto the older implementation. Only a
small, old-API-compatible archive oracle helper and explicit benchmark-only patch
are injected into the baseline; their hashes are recorded. No baseline production
file is changed. Three AB/BA process passes retain their order and raw observations.

Matching uses explicitly enumerated semantic axes, not encoded transport size,
synthetic graph rounds/visits or implementation-derived middle-fact counters.
Production mechanism mappings are reviewed and recorded, rather than choosing
whichever new control happens to be fastest. Owned compatibility wrappers remain
separate comparisons. New shared-handle, digest and preparation-tax stages without
an equivalent old operation remain candidate-only; there is no invented speedup.
Core canonical document/full-trace/directive hashes must agree. ZIP transport and
member content hashes remain exact. SOPack namespace fingerprint version changes
are intentional: its oracle normalizes content identities and compares complete
typed units, sources, assets, frozen imports, exports and producer/root topology,
not archive byte identity between versions. Fixtures document unique source-content
identity requirements used by that normalization.

End-to-end IO is a separate probe, never counted as uninstrumented latency. Selected
CLIs run tiny, large-asset and mostly-unreachable-SOPack workloads cold and warm
under Linux `strace -f -c`; only syscall call/error counts are retained. Events
tracing then runs independently with fresh cold/warm cache states, so its JSONL
writes are not mixed into tracing-off syscall counts. Product fingerprints are
checked across cold/warm and old/new versions. Source/trace files and developer
experiments stay under project `.temp`/`.cache`; no native executable is downloaded
to the developer machine. Candidate store-example counters separately expose actual
acquisition/hash/coalescing work and committed advisory touch batches. Those
primitive counters are not mislabeled as every SQL statement issued by the CLI,
and no syscall-count change justifies weakening publication durability.

### Complete-process corroboration and cold preparation boundary

The full-repair job builds each selected CLI once and reuses it for both probes.
Before instrumentation, three same-runner AB/BA process groups collect five samples
each for `--version`, tiny prompt, 8 MiB asset pack, and SOPack with one reachable
module among 32. Its 31 unreachable macros each contain 16 KiB literal text and
one binding to the same 256 KiB asset: 256 KiB unique asset content, 7.75 MiB
expanded logical asset bytes, and 496 KiB unused literal text (excluding XML
syntax). The independent pack fixture retains its 8 MiB asset. This keeps the
SOPack producer inside the default 64 MiB asset budget without changing that
production policy. Cold and warm cache states are separate: removal of the project
cache and warm priming are excluded from timing; process spawn and exit are included.
OS page cache is uncontrolled. Every product is hashed outside timing and must
match across versions and states. Raw samples and process medians are retained;
no significance claim or sum of component medians substitutes for CLI measurement.

The production linker mapping now targets `link_prepared_facts` and
`link_prepared_clone_plus_call`, reflecting the manager's reusable prepared-unit
path. These are explicitly **warm-fact-reuse** comparisons: one-time proof and
specialization are excluded, unlike the old per-call work. Candidate-only cold
preparation/specialization rows retain complete sample summaries in `unpaired`;
this boundary cannot be hidden or converted into an invented end-to-end speedup.
`middle_shared_prepared_input` is a compatibility middle-end mechanism, not a
claim that the manager specializes the same unit again for every entry.

Release jobs preserve full workspace/all-target/all-feature native contract suites
on ARM and both macOS architectures in the debug profile. This activates bounded
benchmark smoke rather than rerunning hundreds of timing fixtures during release.
All six shipping release binaries are still built with the shipping profile and
receive mandatory native process/archive smoke; exact source CI remains required.
