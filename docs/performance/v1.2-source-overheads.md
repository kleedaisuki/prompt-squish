Evidence: [`v1.2-first-hosted.json`](v1.2-first-hosted.json), candidate commit
`a1ffa142f45db9040a76021cd1fe849b29536b46`, Linux GitHub runner, five paired AB/BA

## Simple actionable source proposals

1. **Shared per-pack include index.** `archive_build::include_closure` rebuilds all import
   adjacency and filters every resolution revision/binding on every included entry. For I
   independent entries, U units and E bindings, this costs O(I*(U+E)) even when each child has
   one reachable unit. Build an owner-to-import index and SourceKey-to-revision index once in
   `pack_bytes`; collect only reachable rows for each child. Expected complexity becomes
   O(U+E + sum(child_reachable_units_and_edges)*log(U)). Retain independent symbol scopes,
   exact snapshot evidence, cycle guards and per-child budgets. The 883 ms total also contains
   512 source compilation/cache writes, so this is not a claim of eliminating the entire cost.
2. **Avoid duplicate trusted-stage validation.** Fresh StaticLinker already validates all
   snapshot units before calling `MiddleEnd::optimize`, which validates each reachable unit
   again. A crate-private validated-input optimization entry can skip only that second pass;
   the public middle API must still validate arbitrary input. Linker image construction and
   `LinkedProgram::reconstruct_optimized` also validate the same image twice; cached public
   reconstruction must retain one full validation. Preserve unreachable-unit validation and
   malformed dependency rejection, rather than globally turning checks off.
3. **Review empty-directive persistence only after phase evidence.** Every ordinary prompt now
   stores a third small CAS output for empty directives and verifies it on warm reuse. This
   may add filesystem/index constants; merely avoiding Vec allocation is unlikely to recover
   milliseconds. Making this output optional changes plan/cache contracts, so defer unless
   traces show this cost warrants the migration. Never omit nonempty directive evidence.
4. **Reduce scalar-analysis allocations.** Selected RenderText regions currently clone region
   operation vectors. Analyze original regions by borrowed IDs; avoid any materialization on
   ordinary no-scalar inputs. This is safe but likely much smaller than filesystem constants.

## Release-profile experiment, not an adopted setting

Cargo's default release profile uses 16 codegen units and only local thin LTO; `lto="thin"`
enables cross-crate optimization. `codegen-units=1` can improve optimizer visibility while
reducing codegen parallelism. Neither setting guarantees lower startup or build time.

Use a hosted environment-only trial (`CARGO_PROFILE_RELEASE_LTO=thin` and
`CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1`) before changing the shipping manifest. Keep the
already-built default binary, compare the same source commit and identical fixtures, record
binary bytes and complete release build elapsed time, and use paired AB/BA measurements.
Run at least 20 startup/tiny repetitions; retain long-tail regex and include cases and all
correctness suites. Do not adopt panic=abort or new CPU target features as part of this trial:
those change failure/platform contracts rather than simply optimizer configuration.

Cross-crate ThinLTO may be valuable for this many-small-domain-crate architecture, but a
profile rebuild invalidates release object caches and increases CI cost. Compare a single
bounded candidate trial first; avoid rebuilding every OS/compiler matrix for speculative
settings. Code/profile changes must remain frozen while the current full run is measured.

  Its application results motivate a trial, not performance claims for xmlsquish.


## Implemented bounded include-graph optimization

`crates/squish-manager/src/archive_build.rs` now builds one immutable `IncludeIndex`
per pack from the already-linked frozen resolution snapshot. Each indexed node
borrows its exact revision and outgoing import bindings; constructing the index
copies no compiled IR. A child projection traverses only its reachable nodes,
retains their original import IDs/revisions, guards cycles, and canonically sorts
its copied evidence. The runtime receives clones only of those child payloads.
Repeated includes still reuse their first rendered bytes within the pack, and
separate included entries still obtain separate linked symbol scopes.

With BTreeMap indexes, construction costs O((U+E) log U). Per-child work now depends
on its own reachable nodes/edges plus canonical ordering and required payload
copying, rather than filtering all U revisions and E bindings again. This targets
the identified I*(U+E) coordination overhead without removing any global parent
snapshot/payload validation or child linker validation. Asset-only packs follow
the same simple index construction path; ordinary prompt builds never construct
an include index.

Pure regression cases cover two disjoint entry scopes, a legal module import
cycle, exact revision and binding preservation, repeated read-only projection,
missing compiled payloads, unknown roots, dangling targets and missing binding
owners. Tests have been authored but are run only by hosted CI. The approximately
883 ms hosted 512-include result above is the pre-optimization baseline; a measured
speedup has not yet been established and must not be inferred from the algorithmic
change alone. The next hosted run should compare the same 512 distinct-entry
fixture and report overall CLI time alongside its pipeline spans.


## Ordinary-prompt sidechannel persistence refinement

After two hosted comparisons showed approximately 8.5–10% higher tiny-cold
latency and phase evidence pointed to cache/publication constants, the shipping
candidate now omits the empty archive-directive CAS output for ordinary prompts.
This is a bounded distribution-specific contract: prompt instantiation declares
`document` and `trace`, archive instantiation declares those plus `directives`,
and backend recipes refer to `directives` only for archives. Fresh prompt results
with nonempty directives fail with the existing MGB150/Emit before any successful
instantiation result or output blobs are recorded. Repeated cold/warm invalid
prompt regression therefore checks that neither instantiation nor backend can
become a cache hit and no prompt product appears.

Output-schema hashing separates the two materialized action keys; existing
three-output prompt records are not eligible for the new two-output plan.
Archive encoding, provenance validation, mutable argument semantics and
persistent sidechannel evidence are unchanged. This avoids generic optional
outputs and does not weaken frontend/linker/runtime validation. Focused plan
contracts cover both prompt spellings and both archive backends, including
backend input recipes and old-schema key separation. Tests run only in hosted
CI; no local Cargo execution was performed. A new paired hosted run is required
to quantify the improvement rather than assuming this removes the complete
observed regression.
