# v1.2 store and orchestration mechanism audit

Date: 2026-10-01. Reference: immutable v1.2.0, commit
`85b68c04c88b6a6b8bce12f1b4e3e10a5a218366`. Status: source evidence,
not a hosted syscall or causal latency measurement.

The in-process core/archive suite intentionally excludes filesystem and manager
orchestration. These remaining mechanisms must not disappear from the audit just
because a compiler microbenchmark cannot reach them.

## Actual production paths

* `VerifiedActionIndex::lookup` in `crates/squish-store/src/action.rs` reads and
  verifies every output through `Cas::get`, then calls `touch` for a SQL UPDATE.
  This is the current runtime path; legacy index methods are not evidence of the
  actual cache-hit algorithm. Cache hits are not read-only.
* `Cas::get` in `crates/squish-store/src/cas.rs` reads the complete blob and
  recomputes its BLAKE3 digest. The consumer can subsequently read the same blob
  again. This integrity boundary is legitimate; repeating verified acquisition
  within one immutable invocation is the optimization question.
* `Cas::put` verifies an existing file before reusing it. A valid hit returns
  before temporary-file creation and sync. It is incorrect to claim that every
  put unconditionally fsyncs. Cold publication writes and synchronizes a
  temporary file, then publishes it with directory synchronization.
* `BuildExecutor::store_blob` in `crates/squish-manager/src/build.rs` computes a
  protocol digest before calling the runtime writer, which hashes the input
  again in the CAS implementation. Its purpose is to check the injected runtime
  contract. Any optimization must retain that contract or explicitly express a
  trusted, digest-bearing immutable buffer capability.
* `linked_for` deep-clones a cached `LinkOutput`. Its fallback additionally
  encodes/hashes cached images while searching. `instantiated_for` clones the
  cached document and complete instantiation output, including provenance.
  This is a representation/ownership question: fixed live output should not
  require copying all unrelated immutable source and IR at every stage.

## Discriminating follow-up

Use Linux hosted `strace -f -yy` on the shipped v1.2.0 binary, telemetry off,
with tiny cold/warm builds and fixed-output closures of 1/16/64 empty imported
modules. Record opens, read/write byte counts, SQLite WAL activity and
fsync/fdatasync by CAS/index/publication path. An independent asset-byte sweep
can expose byte-read amplification. Preserve output-byte oracles and identical
durability settings. Syscall instrumentation measures counts, **not normal
latency**; it must run separately from timing.

No syscall counts or stage speedups have yet been measured. SQL autocommit source
evidence alone does not establish how many filesystem syncs are on the critical
path. WAL checkpoints, existing file state and platform semantics matter.

For future orchestration interventions, Curtsinger and Berger's peer-reviewed
[Coz causal profiling work (SOSP 2015)](https://sigops.org/s/conferences/sosp/2015/current/abstracts.html)
provides the important distinction between observing time in a component and
demonstrating application progress from making that component faster. This task
uses an actual origin-index intervention, not Coz's virtual-speedup instrumentation.
Neither compiler microbenchmarks nor syscall counts establish the whole CLI gain.

## Design implications, conditional on evidence

1. Share immutable linked programs and documents with explicit ownership handles
   across stage consumers, rather than duplicating their complete arenas.
2. Consider invocation-scoped verified blob handles, retaining the persistent
   cache trust boundary and corruption detection for later invocations.
3. Separate advisory LRU bookkeeping from correctness-critical action records;
   any batching must preserve project cache semantics under crashes.
4. Do not improve a benchmark by dropping validation or durability barriers.

SQLite's [atomic commit explanation](https://www.sqlite.org/atomiccommit.html)
and [WAL documentation](https://www.sqlite.org/wal.html) explain why sync removal
is a change of safety contract, not a free performance improvement. The existing
[cache/presentation investigation](cache-and-presentation.md) supplies project
context; this audit narrows its claims to the current verified runtime path.
