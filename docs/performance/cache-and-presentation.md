# Cache semantics are independent of CLI presentation

Status: verified on 2026-09-16 for the human-output change from `694bd18` through
`5c726b3`. The last production presentation change is `8b2f8f0`; `5c726b3` adds only this report.

## Decision

Human output is a projection of the typed event stream. Hiding a digest, shortening it to a display
fingerprint, or showing the complete value at trace verbosity must never change an action key, a
cache lookup, a stored result, or artifact bytes.

The supported presentation policy is therefore:

- normal and short output show product concepts, paths, counts, and cache-hit meaning without full
  digests or internal scheduler identities;
- `-v` may show a short display fingerprint;
- `-vv`, machine JSON, and explicit inspection retain complete identities when diagnosis needs them.

A display fingerprint is not an identity and must not be accepted as a cache lookup key.

## Why the boundary is structural

The following repository boundaries make presentation incapable of defining cache semantics:

1. `crates/squish-cli/src/lib.rs:176-183` stores presentation and execution settings in separate
   fields and explicitly excludes presentation settings from semantic cache keys.
2. `src/main.rs:530-549` constructs `InvocationSettings`, `ManagerCapability`, and `Kernel` without
   passing color, progress, message format, or verbosity. `src/main.rs:728` constructs the renderer
   on the output side of the event sink.
3. `crates/squish-build/src/model.rs:149-179` materializes an action key from its action kind,
   semantic epoch, resolved semantic inputs, canonical options, and output schema. Renderer options
   are not inputs.
4. `crates/squish-manager/src/build.rs:1671-1704` owns the verified action index and opens it through
   `VerifiedActionIndex`; the presentation crate does not.
5. `crates/squish-presentation/Cargo.toml:10-15` depends on the protocol and presentation utilities,
   but not on `squish-build`, `squish-manager`, or `squish-store`. Its `Renderer` consumes an
   already ordered `Event` (`crates/squish-presentation/src/lib.rs:35-37`).

This dependency direction is the main invariant. A test below checks the concrete executable
boundary as well, rather than inferring safety solely from the crate graph.

## Controlled compatibility experiment

Can the post-change executable consume the action index and CAS warmed by the pre-change executable
without recomputation, key drift, catalog-semantic drift, or artifact drift?

### Procedure

1. Build the baseline from a detached worktree at `694bd18`.
2. Create a fresh project and fresh storage roots.
3. Run one cold baseline build with `--message-format=json --emit=prompt --emit=ir --emit=debug`.
4. Run the same baseline executable seven times against the warmed state.
5. Build `5c726b3` independently and run it seven times against the **same** project, action index,
   CAS, source cache, and published target.
6. For every run, parse native v2.1 NDJSON and compare cache-hit action keys, cached result digests,
   published artifacts, and a normalized BuildRecord v2 projection.
7. Query SQLite directly before and after, comparing `actions` without mutable LRU timestamps and
   comparing every `action_results` row.
8. Read the published artifact files and compare independent SHA-256 values, so matching protocol
   metadata alone cannot hide byte drift.

The falsifiers were any missing cache hit, a different action key or result digest, an added or
replaced semantic action-index row, a changed normalized catalog, or changed artifact bytes.

### Build-record metadata variance is intentional

The complete BuildRecord v2 blob digest is **not** expected to remain constant between invocations.
Each terminal record contains the new invocation's `job` and `plan` identities. A cold record also
records worker execution while a warm record records cache result sources. Consequently, the cold
baseline record, warm baseline records, and post-change warm records had distinct content digests.

This is invocation provenance, not compilation cache identity. The comparison therefore removes
only `job` and invocation-derived `plan` identifiers, while retaining the schema, semantic plan
digest, action keys, dependencies, terminal facts, result source, output digests, target generation,
and artifacts. That normalized projection was exactly equal. The action SQLite rows provide a
second independent check that no compiler cache entry was replaced.

Treating the whole BuildRecord digest as an action key would be a category error and would make every
recorded invocation look like a cache miss even when every cacheable compile action was reused.

## Timing observation, not an optimization claim

The seven-run batches had wall-time medians of 104.506 ms (baseline) and 110.782 ms (final
post-change), which is too sensitive to sequential-order and host noise to interpret. Every sample
still reported the same four cache hits. An earlier intermediate presentation revision (`9d8dd43`)
was also measured with 30 alternating AB/BA warmed pairs; its baseline/current wall medians were
128.470/131.987 ms and native event medians were 105.5/111.5 ms.

These debug-build, single-host measurements are not a release-performance equivalence claim. They
do show that timing variation was not evidence of recomputation: every measured run had four cache
hits. Release-profile, cross-platform benchmarking would be required before setting a latency
budget.

## Conclusion and limits

**Observed:** the post-change executable reused all four cacheable actions created by the baseline
executable; keys, cached-result digests, action-index semantics, normalized catalog semantics,
artifact metadata, and artifact bytes were unchanged.

**Mechanistic inference:** because renderer configuration terminates at the event-consumer boundary
and is absent from `KeyRecipe`, changing digest visibility cannot invalidate the compilation cache.

**Limit:** the executable experiment uses one generated project on Windows. It is strong evidence
for binary compatibility across this exact presentation-only change, not a proof for unrelated
future changes to semantic epochs, compiler options, dependency resolution, or artifact schemas.

**Regression rule:** future output-only changes must remain below the protocol event boundary. If a
human-display option appears in `InvocationSettings`, `KeyRecipe`, manager planning, store schema, or
artifact bytes, it is no longer presentation-only and requires an explicit cache migration decision.
