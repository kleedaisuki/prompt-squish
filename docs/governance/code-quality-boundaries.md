# Code-quality and validation boundaries

## Scope and decision

This note records the maintenance rule used for the September 2026 governance pass.
It does **not** supersede the accepted architecture in
[`docs/design/refactor-map.md`](../design/refactor-map.md) or the project-local
layout in [`docs/architecture/target-xmlsquish-layout.md`](../architecture/target-xmlsquish-layout.md).
The product's CLI, file formats, generated bytes, and site UI remain contracts.

| Boundary | Keep / centralize | Avoid |
| --- | --- | --- |
| Untrusted source, manifest, lock, and persisted IR entering a crate | Parse and validate at the entry point; preserve structured diagnostics and resource limits. | Removing a check merely because a current caller happens to validate first. |
| Typed and already-validated internal value crossing a private call | Carry the invariant through a narrow type/API and test the direct public entry separately. | Re-parsing or re-validating the same unchanged value without a new threat or mutation boundary. |
| Filesystem or network effect | Keep authorization, path confinement, content identity, and atomic publication with the owning adapter. | Calling integrity or containment checks “defense in depth” without identifying an attacker-controlled input. |
| Tooling and CI | Share deterministic mechanics; test schemas and ordering without making machine-dependent timings a gate. | Merging historical-release smoke logic with current-head smoke tests when compatibility differs. |

The rule is *boundary validation, not zero validation*. For any proposed deletion,
record: (1) who can control the value, (2) the prior authoritative check,
(3) whether mutation can occur before use, (4) the observable error/format contract,
and (5) a regression test for the public boundary. If any item is unclear, retain
the check. Prefer a small private validated path over an unchecked public API.

## Why this is a measured choice

The [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/dependability.html)
prefer static enforcement through types, then dynamic validation at input boundaries.
That supports typed plans and private validated routes, **not** blanket deletion of
input checks. GitHub's [Actions security guidance](https://docs.github.com/en/code-security/tutorials/secure-your-organization/protect-against-threats)
supports the existing SHA-pinned actions and least-privilege workflow token; these
protect a concrete supply-chain boundary rather than adding local validation noise.

Research is suggestive, not a license for sweeping refactors. A
[2025 large-scale study of architectural complexity](https://research.google/pubs/understanding-architectural-complexity-maintenance-burden-and-developer-sentiment-a-large-scale-study/)
reports correlations between structural complexity and maintenance activity across
1,200+ Google C++/Java projects. Its observational, company-specific setting does
not establish that any particular Rust helper extraction reduces defects. An
[ICSE study of mutation feedback in code review](https://research.google/pubs/please-fix-this-mutant-how-do-developers-resolve-mutants-surfaced-during-code-review/)
finds that some surfaced mutants lead to code or test changes, but also documents
unproductive cases and false positives. Consequently, this pass uses narrow
behavior-preserving diffs and contract tests rather than complexity scores or
test volume as a proxy for quality.

## Verification policy

Use focused crate/tool tests while editing, then the existing MSRV 1.88
workspace checks, architecture-edge check, release verification, site check,
and cross-platform GitHub Actions jobs at a milestone. Keep commits small and
reviewable. Do not stage pre-existing local `.temp` or site package-manager
files that are unrelated to the change.
