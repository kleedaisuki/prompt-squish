# Skills as managed dependencies: prior art and design implications

**Status:** research guidance, not a normative design. **Checked:** 2026-09-29.

## Decision question and local context

How can `xmlsquish` manage repository-local Agent Skills under `.agents/skills/` with Cargo-like `add-skill`/`remove-skill`, local and remote sources, and an `install-skill` command for its own skill, without making dependency state, materialized files, and trust ambiguous?

This repository already has a full package source protocol and a transaction model. [Dependency Source Protocol](../design/dependency-source-protocol.md) distinguishes mutable source selectors, exact locked source identity, verified logical trees, and atomically published materializations. [ADR 0009](../adr/0009-microkernel-manager-and-reusable-ir.md) specifies `--locked`/`--offline`/`--frozen` and transaction recovery for `add`/`remove`. Reuse those semantics rather than inventing a second remote source stack. Existing root [`SKILL.md`](../../SKILL.md) is the source for xmlsquish's own installable skill. Current [CI](../../.github/workflows/ci.yml) already runs cross-platform Rust checks on GitHub Actions.

## Primary evidence

| Source | Established fact | Consequence for xmlsquish |
| --- | --- | --- |
| [Agent Skills specification](https://agentskills.io/specification) | A skill is a directory containing `SKILL.md`, YAML frontmatter with required `name` and `description`, and optional arbitrary support files. The `name` must match its parent directory; the normative name restrictions and limits are explicit. | Validate the *whole bundle* and frontmatter, not just the presence of a Markdown file. Materialize at `.agents/skills/<validated-name>/SKILL.md`; never silently rename metadata. |
| [GitHub Copilot skill documentation](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-skills) | `.agents/skills/` is an accepted repository scope (alongside `.github/skills/` and `.claude/skills/`), with one directory per skill. Skills may have supporting scripts/assets. | The requested path is an interoperable product location, not merely an internal cache. It must remain human-readable and committed/reviewable if users choose to track it. |
| [Cargo dependency specification](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html) and [`cargo add`](https://doc.rust-lang.org/cargo/commands/cargo-add.html) | Cargo accepts registry, Git, and exact local path sources. A Git branch/tag is locked to a commit; a local path names the exact package directory, not an arbitrary repository to search. | Keep source selectors explicit and disjoint (`--path`, `--git`/ref, registry). For local skill installation, require the exact skill directory or a clearly defined single-file `SKILL.md` form; don't recursively search and select a surprising match. Lock remote bytes/commit; treat editable local paths as live inputs rather than pretending they are immutable. |
| [OpenAI Skills security guidance](https://developers.openai.com/api/docs/guides/tools-skills#risks-and-safety) | Skills influence planning and tool execution; they are privileged instructions and potentially executable scripts. Developers should inspect skills before exposure, and gate sensitive actions. | Installation validation and content integrity are necessary but do **not** establish safety. Show source and installed files in dry-run/confirmation output, do not execute scripts at install, and document that users must review third-party skills. |
| [Liu et al., USENIX Security 2026](https://www.usenix.org/conference/usenixsecurity26/presentation/liu-yi) | A study of 98,380 registry skills found 157 confirmed malicious skills using static and dynamic verification; documented modes include credential theft and adversarial instructions. This is an observed sample, not an ecosystem-wide base rate. | Treat skill installation as a supply-chain trust boundary. No automatic activation/privilege escalation; source provenance and exact content identity belong in lock/diagnostics. |
| [Schmotz et al., SkillInject, 2026 preprint](https://arxiv.org/abs/2602.20156) | A 202-pair benchmark reports high prompt-injection success for tested agents and argues that simple filtering is insufficient. Preprint/benchmark result, not a universal failure probability. | Do not market frontmatter scanning as security. A future policy/authorization layer is distinct from package management; manage content reproducibly now and avoid implicit trust elevation. |
| [OpenSSF repository-security principles](https://repos.openssf.org/principles-for-package-repository-security.html) | Repository trust calls for integrity, provenance, and controls across publishing, distribution, and consuming stages. | Retain logical origin plus immutable digest/commit in lock and user-facing inspection; a digest proves byte identity, not publisher trust. |

## Model recommendation (inference from sources and local architecture)

Keep three distinct entities, even if one command updates all three:

1. **Declaration:** skill name and an explicit source selector in project manifest state. This is user intent. An optional Git ref/registry version may be movable.
2. **Lock:** exact remote identity (commit and subtree/content digest, or registry version/archive and tree digest). This is reproducibility. A local path dependency remains a live path and must be documented as such.
3. **Projection:** `.agents/skills/<name>/` is the user- and agent-visible installed tree. A private cache may deduplicate verified bytes, but must not be the only human-facing path. The projection should record ownership so removal never deletes a pre-existing manually maintained skill.

Suggested flow: resolve and validate source into an immutable logical skill tree; reject path escape, traversal, symlink/reparse-point escape, case-fold collisions and unsupported special files; preflight destination ownership/collisions; stage manifest, lock, and projection changes; publish/recover as one logical transaction. This follows the existing source protocol's common-tree boundary. Preserve unrelated manual files in `.agents/skills/` and refuse an overwrite unless the semantics explicitly identify adoption/replacement. Local `--path` inputs need a stated copy-vs-link choice: a *copy snapshot* gives deterministic installed bytes but requires explicit update/sync; a *symlink* tracks edits but breaks portability and permits mutable external content. Prefer a managed copy for the product projection and preserve the declared local source path for future refresh; document that the path's current contents are not frozen by `--frozen`.

`install-skill` is conceptually different from `add-skill`: it installs the tool's own bundled skill and need not create a third-party project dependency or contact a registry. Give its destination/scope and overwrite/upgrade behavior an explicit contract. `add-skill` and `remove-skill` should be symmetric declaration edits with lock/projection synchronization, and share `add`/`remove` flag meanings where applicable. Name conflicts between a dependency and a manual skill must be errors, not a silently chosen winner; Copilot's [CLI reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference) explicitly has precedence among several skill roots, which means silently installing to a lower-priority location may not activate what the user expects.

## Tests worth putting in hosted CI

The repository's existing Linux/Windows Actions matrix is an appropriate venue for integration tests without consuming the developer's disk. Add fixture-level tests for: local skill with assets/scripts; remote Git ref pinned despite subsequent ref movement; `--locked`/`--offline`/`--frozen` semantics; duplicate names and manually owned destination; invalid frontmatter/name mismatch; path traversal, symlink/reparse point, case-insensitive collisions; interrupted install/remove and recovery; and no install-time script execution. Keep CI permissions read-only for PR tests, avoid secrets in untrusted-code jobs, and pin third-party actions by immutable SHA, consistent with [GitHub Actions secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use) and the repository's existing workflow. Run Windows as a real host: path and rename behavior cannot be validated by Linux-only tests.

## Open product decisions to resolve before implementation

* **Manifest syntax:** dedicated `[skills]` namespace versus a separate file; keep it separate from XML package `[dependencies]` because these are agent instruction bundles, not `pkg:` importable modules.
* **Source scope:** whether registry-distributed skills are actually supported by a live skill registry. Cargo-like syntax does not imply there is a trustworthy registry endpoint. If none exists, do not manufacture a default registry or accept ambiguous bare names.
* **Lock/projection ownership:** exact scheme for identifying a managed projection and recovering user edits. Avoid deleting user modifications on `remove-skill`; an integrity mismatch should yield a conflict or explicit force path.
* **Tool-skill versioning:** whether `install-skill` copies from the running executable's embedded asset or from a source checkout. Runtime-bundled bytes make behavior independent of cwd and Git checkout; the root `SKILL.md` can remain the authoring source at build time.

## Frontmatter parser selection (2026-09-29)

The original [`serde_yaml` repository](https://github.com/dtolnay/serde-yaml/releases) is archived and its maintainer explicitly stopped releases. The official YAML organization now maintains [`yaml_serde`](https://github.com/yaml/yaml-serde), while [`yaml-rust2`](https://github.com/Ethiraric/yaml-rust2) offers a pure-Rust YAML parser with a stated stable/basic-maintenance policy. The implementation selects `yaml_serde` for bounded `SKILL.md` frontmatter and typed required-field deserialization. Parse the header as actual YAML, then require `name` and `description` to be strings; a line splitter would misread comments, block scalars, or non-string values. This is an implementation choice, not evidence that third-party skill contents are safe.
