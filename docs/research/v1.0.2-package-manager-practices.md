# v1.0.2 package-manager storage, cleaning, CI, and release practices

**Status:** implementation guidance, not a normative compatibility contract  
**Research date:** 2026-09-17  
**Decision target:** the `xmlsquish` v1.0.2 storage-layout, `clean`, cross-platform CI, and release work

## 1. Question and repository context

The immediate usability defect is not that content-derived identities exist. They are useful for
integrity, cache reuse, and atomic publication. The defect is that the current project-local
publication root makes those implementation identities visible as the apparent product layout:

```text
target/xmlsquish/.squish-publish/
  generations/<target-hash>/<generation-hash>/artifacts/...
  targets/<target-hash>/current.json
```

The repository already has the right *logical* split: a global content-addressed store (CAS) and
action index, project-scoped catalog state, and a project-local publication root. It also already
uses typed logical locators such as `target/xmlsquish/chat.prompt` in presentation and inspection.
The missing step is to make that logical locator a real, boring filesystem path for the dominant
user workflow, while keeping transactional generation machinery private.

This note answers five narrower questions:

1. Where do mature tools put final artifacts versus caches and intermediate state?
2. When are hashes appropriate in paths, and when are they user-interface leakage?
3. What should `clean` mean, especially for stale dependencies in shared storage?
4. What constitutes useful cross-platform Rust CI rather than merely cross-compilation?
5. How should a tag create a complete GitHub Release without giving build jobs write access?

The recommendations assume that CAS objects and downloaded dependencies are reproducible caches,
that a build catalog can be reconstructed, and that `target/xmlsquish` is not an archival store.
If any of those assumptions changes, the relevant deletion policy must change too.

## 2. Direct evidence from mature tools

| System | Observed official behavior | What it establishes for `xmlsquish` |
| --- | --- | --- |
| Cargo | Final binaries are directly under `target/debug` or `target/release`; dependency and compiler internals live under `deps`, `incremental`, and `build`. Cargo explicitly calls the latter layout internal and subject to change. [`Build Cache`](https://doc.rust-lang.org/cargo/reference/build-cache.html) | Stable, human-readable final paths and opaque internal paths can coexist. A hash is acceptable below a private subtree, not as the only route to the product. |
| Cargo | `cargo clean` removes the complete target directory by default and supports `--dry-run`, package, profile, target, and documentation selection. [`cargo clean`](https://doc.rust-lang.org/cargo/commands/cargo-clean.html) | The default project clean should be unsurprising and project-scoped; previews and narrower selectors are valuable, but a global cache purge should not be smuggled into the default. |
| Cargo | The global Cargo cache periodically deletes unused network material after three months and locally regenerable material after one month; offline/frozen operation suppresses automatic deletion. Build-artifact tracking is not yet included. [`Cargo configuration: cache`](https://doc.rust-lang.org/cargo/reference/config.html#cache) | Age-based global cache maintenance is acceptable, but it is distinct from project output cleaning and must respect offline expectations. |
| npm | Local packages appear in the familiar project-local `node_modules`, while HTTP/package cache data resides in an opaque, content-addressed `_cacache` under a platform user-cache path. Reads and writes are integrity checked; corrupt entries are refetched. [`npm cache`](https://docs.npmjs.com/cli/cache/) and [`folders`](https://docs.npmjs.com/files/folders/) | Content-addressing belongs behind a cache boundary. A cache is disposable and must not be the sole authoritative copy of user output. |
| npm | `npm cache verify` checks integrity and garbage-collects unneeded cache data; full cache deletion is normally unnecessary. Separately, `npm prune` removes packages installed on disk that are no longer in the declared dependency set and offers `--dry-run`. [`npm cache`](https://docs.npmjs.com/cli/cache/) and [`npm prune`](https://docs.npmjs.com/cli/v7/commands/npm-prune/) | “Prune stale dependencies” and “delete the cache” are different operations. Verification/GC should be preferable to indiscriminate cache removal. |
| pnpm | Package files are hard-linked from a content-addressable store into a project-local virtual store; ordinary package names remain available through links. [`Symlinked node_modules structure`](https://pnpm.io/symlinked-node-modules-structure) | Deduplication does not require users to navigate content hashes. A friendly projection can point at immutable backing content. |
| pnpm | `pnpm store prune` removes packages unused by any project, reports freed size, and is safe because future installs can redownload them. The documentation recommends occasional, not frequent, pruning because branch switching may reuse old versions. Current global-store mode uses registered projects and mark-and-sweep collection. [`pnpm store`](https://pnpm.io/cli/store) | Shared dependency cleanup needs system-wide liveness, not just the current lockfile. Report reclaimed space and avoid eagerly deleting recently unused versions. |
| Go | The build cache defaults to the OS user-cache directory, is concurrency-safe, periodically removes old data, and normally does not require manual cleaning. Downloaded modules live in a distinct shared module cache. [`go command`](https://pkg.go.dev/cmd/go) and [`Go Modules Reference`](https://go.dev/ref/mod#module-cache) | Keep build results, dependency source, and final output as distinct storage classes with distinct clean policies. |
| Go | `go clean` has separate flags for build cache, test cache, module cache, and fuzz cache. `go mod tidy` instead edits the declared dependency graph, adding required modules and removing unused ones. [`go clean`](https://pkg.go.dev/cmd/go) and [`Managing dependencies`](https://go.dev/doc/modules/managing-dependencies#synchronizing-your-codes-dependencies) | Physical cleanup must not silently rewrite dependency intent. Manifest/lock synchronization belongs to dependency commands, not `clean`. |
| Bazel | The heavy output base is outside the workspace, while convenient `bazel-bin`, `bazel-out`, and test-log links expose useful views. The layout requirements explicitly include easy access, unambiguous identities, concurrent workspaces, and selective cleanup. [`Output directory layout`](https://docs.bazel.build/versions/main/output_directories.html) | A complex private layout should be projected through a simple user-facing view. The projection is a product surface; the backing tree is not. |
| Nix | Store collection is reachability-based: paths reachable from declared GC roots are retained; dead paths may be previewed and collection may stop after a requested amount of space is freed. [`nix-store --gc`](https://nix.dev/manual/nix/2.31/command-ref/nix-store/gc) | Mark-and-sweep from durable roots is a sound model for a shared CAS. A dry run and byte budget make destructive maintenance inspectable and bounded. |

### 2.1 Synthesis: three storage planes

The strongest common pattern is not a particular directory spelling. It is a separation of
semantics:

| Plane | Naming | Lifetime | User expectation |
| --- | --- | --- | --- |
| **Product view** | package/target/artifact names | until rebuild or project clean | directly open, copy, diff, inspect, or script against it |
| **Project state** | typed internal identities; hashes allowed below a hidden boundary | until superseded, recovered, or project clean | tool-owned, crash-recoverable, not an API |
| **Shared cache** | content/action digests | opportunistic and reclaimable | may disappear without semantic data loss |

Trying to encode all three planes in one physical tree is what produces unnecessary nesting and
hashes in user workflows. The cure is not to remove content identities; it is to stop treating the
CAS/generation representation as the product view.

## 3. Recommended v1.0.2 layout

### 3.1 User-visible contract

For a target named `chat`, materialize selected current artifacts directly under the configured
target directory:

```text
target/xmlsquish/
  chat.prompt
  chat.xsir       # only when requested
  chat.psdbg      # only when requested
  .state/         # private; spelling and contents are not API
```

If two packages or two targets can legitimately emit the same basename, add exactly one semantic
level, not a chain of mechanical levels:

```text
target/xmlsquish/<package>/<target>.prompt
```

Do not place target digests, generation digests, action digests, or manifest file names in the
logical locator. Preserve the already documented invariant that a locator remains stable as its
bytes and generation change.

The preferred default is the flat form because the current product is a single-package manager and
the dominant artifact is already named by target. Introduce the package level only when a real
collision domain requires it. This follows Cargo's approach: semantic profile/target categories are
visible; compiler bookkeeping is not.

### 3.2 Private transactional state

Generation manifests, commit journals, locks, and immutable staging trees may remain hash-addressed,
but move or rename them behind one private boundary such as `target/xmlsquish/.state/`. The exact
spelling is less important than these invariants:

1. No normal command output instructs a user to enter the private tree.
2. `inspect artifact <logical-path>` resolves through the typed catalog rather than scanning it.
3. A successful build atomically advances the complete logical product view; a crash exposes either
   the old complete view or the new complete view, never a mixture.
4. Private state can change incompatibly across versions and can be rebuilt or migrated without
   changing logical paths.
5. Directory walkers, release packaging, and examples exclude the private subtree unless explicitly
   diagnosing internals.

A crucial implementation detail is that atomicity must be defined over the visible artifact set,
not merely over a hidden `current.json`. Possible implementations include a stable directory swap,
stable symlinks/junctions where platform behavior is acceptable, or individually materialized files
whose catalog switch remains the authority. Choose the simplest cross-platform implementation that
preserves the repository's existing crash-recovery tests. Do not weaken whole-generation recovery
just to make the tree prettier.

### 3.3 Shared cache and dependency materialization

Keep these below the configured manager/source storage roots, normally a platform user cache/state
directory rather than the project target:

```text
<storage-root>/
  cas/<digest...>
  actions/<action-key...>
  catalog/projects/<project-id...>/
  sources/<source-id...>/
```

Hashes are appropriate here because equality and immutability are the semantics. Users should reach
this state through commands (`inspect`, `clean --stale`, future `cache verify`) rather than by path
construction. The existing per-project catalog digest is therefore not itself a defect; exposing it
as the ordinary artifact route would be.

## 4. `clean` contract

### 4.1 Separate deletion domains

The minimal coherent CLI is:

```text
xmlsquish clean                 # remove this project's complete target directory
xmlsquish clean --dry-run       # report paths/count/bytes, change nothing
xmlsquish clean --stale         # also prune globally unreferenced dependency/cache state
```

If finer controls are already needed by the product, add orthogonal flags rather than special-case
commands:

```text
--artifacts      project product view and private publication state
--stale          unreachable dependency materializations and cache records
--max-freed SIZE bound global reclamation
```

Default `clean` should imply `--artifacts`. Whether v1.0.2 makes `--stale` part of the unqualified
default is a product choice, but the evidence favors keeping it explicit: Cargo and Go keep global
cache deletion separate, while pnpm warns that over-frequent pruning harms branch-switch performance.
The user request to remove both outputs and invalid dependencies can still be satisfied by documenting
`xmlsquish clean --stale` as the complete cleanup form.

### 4.2 Define “stale” by reachability, not age alone

For shared dependency and CAS storage, a candidate is stale only if it is not reachable from any
durable live root known to the manager. Roots should include at least:

- every registered project's current valid lock graph;
- every current build-catalog generation retained for inspection/recovery;
- any in-progress operation lease or journal needed to survive a concurrent clean;
- optionally, a small number or age window of previous good generations if rollback is supported.

Then perform a conventional mark-and-sweep:

```text
snapshot roots under the store lock
  -> mark referenced source packages, blobs, actions, and generations
  -> exclude live leases / active staging directories
  -> sweep only unmarked entries older than the grace period
  -> report item counts and bytes reclaimed
```

Age is a *second* guard against racing a just-created object; it must not substitute for liveness.
A dependency absent from the current project's lockfile may still be live for another project.

### 4.3 Concurrency and crash behavior

`clean` is itself a mutating manager operation and should use the same typed request, kernel lifecycle,
and deterministic event/reporting path as other commands. It should not become an ad-hoc `remove_dir_all`
in `main`.

Required behavior:

- Serialize project-target deletion against publication, or make publication reopen/recreate the
  target root normally after the deletion decision.
- Coordinate shared pruning with writers using the existing store locking/lease abstraction. Do not
  infer liveness from incomplete directory names.
- Missing target/cache entries are successful no-ops, making repeated clean idempotent.
- A failure to delete one entry is reported with its path/category and does not falsify the count of
  successful deletions.
- Symlinks/junctions are removed as directory entries; `clean` must never follow them outside the
  validated project/storage root.
- Recovery journals are either completed before deletion or deleted together with the complete
  owned namespace. Never leave a current pointer whose generation was swept.
- Human output reports categories, totals, and reclaimed bytes; structured output emits the same
  facts rather than reparsing prose.

### 4.4 What `clean` must not do

- Do not edit `xmlsquish.toml` or the lockfile. That is `remove`/resolution/tidy behavior.
- Do not delete a globally shared package merely because the current project stopped using it.
- Do not make a build depend on cache persistence; any swept cache object must be fetchable or
  rebuildable.
- Do not require users to know a hash or a private generation path.
- Do not delete source inputs, configured output directories outside validated ownership, or
  credentials/configuration.

### 4.5 Focused acceptance matrix

| Scenario | Required observation |
| --- | --- |
| Clean before first build | Success, zero removed, no new target tree created. |
| Clean after build | `target/xmlsquish` and private publication state are absent; sources/manifests remain. |
| Repeated clean | Same successful semantic result; second invocation reports zero. |
| `--dry-run` | Same planned categories/counts as real clean, with byte estimates; no filesystem changes. |
| Build after clean | Recreates friendly artifact paths and succeeds from either warm or cold shared cache. |
| Two projects share a dependency | Cleaning/pruning project A does not break an offline build of B while B remains a registered live root. |
| Stale old dependency | After no live root references it and the grace condition is met, `--stale` removes it and reports reclaimed bytes. |
| Concurrent build and clean | No partial visible generation, dangling current pointer, or deleted live CAS blob. |
| Interrupted publication | The next clean/build takes the existing recovery path and converges; it does not ask the user to repair directories. |
| Windows aliases and long paths | No path escapes, case aliases, junction traversal, or permanently locked tree; the same logical behavior holds on Linux/macOS/Windows. |

## 5. Cross-platform Rust CI

### 5.1 What to test

GitHub's matrix strategy is explicitly intended to run a job over operating-system/toolchain
variations, and `fail-fast: false` preserves all platform evidence in one run. See
[`Running variations of jobs`](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/run-job-variations)
and the [workflow syntax reference](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstrategy).

For this project, the minimum PR/push evidence is:

| Job | Runner(s) | Purpose |
| --- | --- | --- |
| Quality/MSRV | Ubuntu, Rust 1.88 | `cargo check --locked`, format, strict Clippy, architecture checks; proves declared minimum version rather than current stable. |
| Native tests | `ubuntu-latest`, `windows-latest`, `macos-latest`, Rust 1.88 | Build and run the complete workspace and root-process tests on each supported OS. Native execution matters for paths, PTY/ConPTY, rename, file-lock, and cleanup behavior. |
| Root smoke | same three OSes | Exercise the composed executable, friendly layout, `clean`, and rebuild; crate unit tests alone cannot prove composition. |
| Site | Ubuntu, locked Node dependencies | Preserve current documentation/product-site checks. |

Rust classifies Tier 1 host targets as guaranteed development platforms with automated compiler and
tool tests. That makes the common Linux and Windows x86-64 hosts a sound baseline; Apple host targets
remain essential product evidence even where their current tier listing differs. See the
[`rustc` platform support policy](https://doc.rust-lang.org/rustc/platform-support.html).

Use `--locked` everywhere in CI and release builds. Cargo documents `--locked` as the mechanism that
fails rather than silently changing the lockfile, which is specifically useful for deterministic CI
([`cargo remove` manifest options](https://doc.rust-lang.org/cargo/commands/cargo-remove.html#manifest-options)).
Keep the selected toolchain in the checked-in `rust-toolchain.toml`; rustup explicitly supports
version-controlled directory toolchain files and component declarations
([rustup overrides](https://rust-lang.github.io/rustup/overrides.html#the-toolchain-file)). GitHub's
own [Rust build-and-test guide](https://docs.github.com/en/actions/tutorials/build-and-test-code/rust)
also demonstrates locked dependency caching and Cargo test steps, but the repository's MSRV and
three-OS requirements should remain stricter than that introductory template.

### 5.2 Caching without making cache hits correctness requirements

GitHub distinguishes dependency caches, which are regenerable accelerators, from workflow artifacts,
which transfer or preserve job products. A job must remain able to rebuild when no cache exists.
See [Dependency caching](https://docs.github.com/en/actions/concepts/workflows-and-actions/dependency-caching)
and [Workflow artifacts](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts).

For Rust, a cache key must include at least OS, toolchain identity, relevant build mode/features, and
the `Cargo.lock` hash. Avoid restoring one operating system's `target` directory onto another.
Caching Cargo registry/git downloads is lower risk than caching all target outputs. If target outputs
are cached, keep keys strict and ensure tests still run after restoration.

The current workflows' full-length action SHA pins are aligned with GitHub guidance: a full commit
SHA is the only immutable way to reference an action. See the
[GitHub secure-use reference](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions).

## 6. Tag-driven GitHub Release

### 6.1 Release topology

Use one tag-triggered workflow with three stages:

```text
resolve and validate v1.0.2 tag
  -> native build/test/package matrix (read-only token)
  -> aggregate/checksum/publish job (contents: write)
```

GitHub's `push.tags` filter is the native mechanism for selecting tag refs; when only `tags` is
defined, ordinary branch pushes do not trigger that workflow. See the official
[tag-filter syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushbranchestagsbranches-ignoretags-ignore).

Only the final job should receive `contents: write`; GitHub documents that permission as the ability
to create a release, and unspecified permissions become `none` when an explicit permission map is
used. See [workflow permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions).

The build matrix should package conventional, stable asset names such as:

```text
xmlsquish-v1.0.2-x86_64-unknown-linux-gnu.tar.gz
xmlsquish-v1.0.2-aarch64-apple-darwin.tar.gz
xmlsquish-v1.0.2-x86_64-pc-windows-msvc.zip
SHA256SUMS
```

Every matrix job must run tests natively where the runner/target pair permits it, smoke-test the
packaged executable (including `--version`), and upload one uniquely named workflow artifact. The
final job downloads all matrix artifacts, verifies the expected target set exactly once, recomputes
checksums, and publishes only after all build jobs succeed.

GitHub's upload-artifact implementation makes uploaded workflow artifacts immutable and exposes a
SHA-256 artifact digest. Unique per-target names therefore fit the aggregation design; artifacts and
release assets still serve different lifetimes. See the official
[`actions/upload-artifact` README](https://github.com/actions/upload-artifact#outputs).

### 6.2 Tag and version invariants

Before building or publishing, require all of the following:

1. Tag grammar is exactly stable SemVer, e.g. `v1.0.2`, unless prerelease support is intentional.
2. The tag already exists remotely and resolves to the exact source commit being built.
3. The tag version equals root `Cargo.toml` package version, CLI `--version`, changelog/release-note
   identity, and any website release record used as an asserted source of truth.
4. The workflow builds the tag commit, not the moving default branch. Automation helpers may be
   checked out separately, but must not change source-package semantics.
5. Publishing refuses to replace an existing release asset with different bytes.

`gh release create --verify-tag` is the official CLI guard that aborts if the tag does not already
exist; the command can attach assets and use a notes file or generated notes. See
[`gh release create`](https://cli.github.com/manual/gh_release_create). Prefer checked-in v1.0.2
release notes when the repository already maintains curated release documents; generated notes may
supplement but should not contradict them.

### 6.3 Provenance as a follow-up, not a release blocker

GitHub artifact attestations can bind a binary to its Actions build provenance. They require
`id-token: write`, `contents: read`, and `attestations: write`, and consumers can verify with
`gh attestation verify`. See
[Using artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations).

This is a valuable next increment after correct multi-platform packaging and checksums. It should
not complicate the initial release path unless verification instructions and permission boundaries
are also documented and tested.

## 7. Repository-specific review of the current automation

At the research snapshot, `.github/workflows/ci.yml` already has the important baseline properties:

- read-only workflow permissions;
- a dedicated MSRV 1.88 quality job;
- native Linux, Windows, and macOS test jobs with `fail-fast: false`;
- composed CLI smoke testing and Linux source-install smoke;
- locked site installation and checks.

The current `.github/workflows/release.yml` is also structurally aligned with the recommendation:

- stable-tag resolution to an immutable commit;
- six native architecture/OS packages;
- read-only build jobs and a separate write-enabled publisher;
- tag-source checkout distinct from automation checkout;
- native release tests, packaging smoke tests, uniquely named workflow artifacts, and final
  aggregation;
- full-length SHA pins for actions.

Therefore the v1.0.2 implementation should focus validation on the remaining product invariants,
not rewrite a working pipeline merely for stylistic uniformity: confirm version equality, asset-set
completeness, checksums, non-overwriting publication, packaged `--version`, and an actual tag/manual
dry run. CI should add `clean` and friendly-layout behavior to the root smoke/regression suite.

## 8. Adversarial review and trade-offs

| Tempting approach | Strongest case for it | Why it is still rejected or constrained |
| --- | --- | --- |
| Delete generation/CAS machinery and write final files directly | Produces the prettiest tree with the least code. | It discards already tested atomic generation and crash recovery. Hide complexity; do not erase necessary durability semantics. |
| Leave hashes in place and merely suppress them in CLI output | No migration or publisher changes. | Users still encounter the layout in editors, file dialogs, scripts, packaging, and clean operations. Presentation-only hiding does not satisfy the filesystem UX problem. |
| Make `clean` delete all global state | Maximizes reclaimed disk and is easy to explain. | It harms other projects and offline work, and conflates project output with shared cache. Go/Cargo/pnpm all distinguish these domains. |
| Decide stale state from the current lockfile | Easy to implement locally. | Incorrect under multiple projects, branch switching, concurrent builds, and retained generations. Shared-store GC needs global roots or conservative age-based cache policy. |
| Keep every historical generation forever | Simplifies rollback and avoids GC races. | Unbounded target growth is a user-visible operational defect. Retain only what recovery/rollback contracts actually require. |
| Cross-compile all assets from one Linux job | Cheap and deterministic tool setup. | It does not execute Windows/macOS path, terminal, locking, packaging, or cleanup behavior. Native tests are required for this project. |
| Let each matrix job publish its release asset | Simple fan-out. | It grants six jobs write permission and permits partial releases. Aggregate first; publish exactly once after completeness checks. |

## 9. Recommended implementation order

1. Freeze the logical target-directory contract and collision policy with process tests.
2. Change publication so friendly files are the ordinary product view while `.state` retains atomic
   generation and recovery implementation details.
3. Add `clean` through protocol/kernel/manager/runtime layers; make plain clean idempotently remove
   the project target tree.
4. Add `--dry-run` and structured deletion totals.
5. Add conservative shared stale pruning only after durable roots and concurrent leases are explicit;
   otherwise ship project clean first rather than guessing global liveness.
6. Extend Linux/macOS/Windows root smoke tests with build -> inspect friendly path -> clean -> rebuild.
7. Validate tag/version/asset/checksum invariants in the existing release topology and run the
   manual/tag release rehearsal for v1.0.2.

## 10. Bottom line

The industry consensus is remarkably consistent: **semantic names are for products; hashes are for
stores**. Cargo exposes final binaries above hashed dependencies, pnpm projects friendly names over a
content-addressed store, Go moves caches into platform user directories, Bazel supplies convenient
workspace views over a complex output base, and Nix collects shared immutable objects by reachability.

For v1.0.2, retain the verified CAS and generation model, but make
`target/xmlsquish/<target>.<kind>` the real, stable path. Make plain `clean` remove project-owned
outputs, and make stale shared-dependency collection an explicit, reachability-aware extension with
dry-run and byte reporting. Prove the filesystem and cleanup behavior natively on Linux, Windows, and
macOS, then let a single least-privilege aggregation job publish the complete tag release.
